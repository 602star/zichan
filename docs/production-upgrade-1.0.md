# 从 0.2.0 到 1.0.0 的生产部署与一键更新方案

本方案以本仓库的 `0.2.0` 本地发布包为起点。下一次计划版本为 `1.0.0`；`0.2.0` 不包含自动升级功能。方案参考了《TS_Docker_Web_一键更新技术方案》，并按本项目的 Docker 镜像、SQLite 和多节点复制结构调整。

## 现有边界

- Docker 镜像同时提供 Web 和同步服务，数据位于 `/state/server`。镜像当前由 Compose 在目标机从源码构建，未接入镜像仓库。
- `0.2.0` 的服务器数据库基线为 schema 27，本地账本基线为 schema 127，同步协议为 v3。现有启动检查只接受当前 schema；跨版本数据迁移必须在 `1.0.0` 实现和验证。
- 数据库、加密附件、`server.secret`、`custody.key`、`node-signing.key`、`server-id` 和 `opaque.server-setup` 必须随节点一起备份。恢复副本不得与原节点同时在线。
- Web 的 Service Worker 可能继续运行旧页面。服务器与旧 Web、桌面客户端之间需要明确的兼容窗口。

## 生产部署目标

每台 Linux 主机的 Compose 只运行一个业务容器；HTTPS 反向代理作为宿主机服务运行，只开放 443。业务服务通过宿主机网络仅监听 `127.0.0.1:8787`，反向代理转发到该地址、保留公共 Host，并覆盖 `X-Forwarded-Proto` 为单一的 `https`。`TRUSTED_PROXIES` 精确设为实际代理地址 `127.0.0.1`。每台节点使用独立的持久数据目录与节点身份。

建议将部署配置、业务状态和备份分开：`/etc/zichan/` 保存 Compose 和更新策略，`/srv/zichan/state/` 挂载到 `/state`，`/srv/zichan/backups/` 挂载到 `/backups`，再把加密备份复制到异机。首次生成的 `server.secret` 固定保存；重启和重建容器必须复用数据卷，不临时生成另一把 `SYNC_SECRET`。生产 Compose 使用经验证的镜像 digest，而不是在主机上拉取可变标签后直接启动。

## 1.0.0 的 Web 一键更新架构

采用参考方案中的版本检查、管理员操作、异步任务、进度和审计界面；执行层采用**镜像级更新**。不采用将新程序写入容器可写层或程序 Volume 的方案，因为它会让运行版本、镜像版本及容器重建后的行为分离。

```text
Owner 管理页面 → 更新任务 API → 持久化更新请求
                                  ↓
宿主机部署执行器 ← 只读取限定范围的任务与发布清单
      ↓
验证签名和镜像 digest → 拉取镜像 → 排空写入 → 停服务
      ↓
备份并校验 → 运行迁移 → 启动新镜像 → 版本和健康验收
      ↓
提交成功记录，或按回滚边界恢复
```

执行器是主机侧的独立服务，由 `systemd` 管理；Docker Socket 不挂进业务容器。业务 API 只能提交预定义的目标版本任务，不能传入任意 URL、镜像名、路径或 Shell 命令。执行器独立保存任务状态，所以新服务启动失败时仍能报告和恢复。更新页面只允许 Owner 在重新验证身份并满足管理员 MFA 后触发；读取状态可授予较低管理权限。所有更新、回滚及失败原因进入管理审计。

发布源适配层读取签名发布清单，并可分别接入 GitHub Releases、自建 Git 服务或自建更新站点。清单至少声明版本、通道、平台、镜像 digest、服务器 schema 的来源与目标版本、支持的最小客户端版本和下载大小。私有源凭据只留在主机执行器，不送到浏览器、业务容器日志或数据库。镜像和清单都需验证来源与完整性。

## 更新状态与顺序

状态为 `checking → available → pulling → verifying → draining → backing_up → migrating → starting → validating → succeeded`；任一步失败记录错误和可执行的恢复路径。任务具有持久 ID、幂等键和主机互斥锁。管理页面断线后通过任务 ID 重新查询，不将连接中断直接当成失败。

1. 预检：确认当前 `0.2.0` 身份、schema 27、镜像 digest、磁盘空间、备份目录写权限和目标发布签名；多节点部署还需确认副本组状态与其他节点没有更新任务。
2. 拉取并验证 `1.0.0` 镜像，不改动当前运行容器。
3. 宿主机执行器先取得与自动备份执行器共用的维护互斥锁，再读取 `backup-executor.json` 的状态与心跳并再次确认；状态为 `running`、心跳失联或状态不可读时不停止容器，等待备份完成或推迟更新。自动备份在认领时间窗口前也须检查同一把锁，消除检查与停服之间的竞态。随后进入维护状态，拒绝新写入并等待在途写入完成。
4. 优雅停止服务；用**旧版本维护入口**创建独立完整备份并校验数据库、附件和密钥文件。备份失败即恢复原服务，停止更新。
5. 由独立迁移器从 schema 27 逐步迁移至 `1.0.0` 目标结构。每步在事务内记录版本，拒绝未知或不完整结构；不清空原数据目录。
6. 用目标镜像启动唯一实例，在维护状态下核对版本、schema、`serverId`、节点公钥、`/api/ready`、Web 页面和代表性同步读取。通过后开放写入，记录成功 digest；开放后的写入问题按下述回滚边界处理。
7. 同步组逐台更新，上一台回到 `READY` 后才更新下一台。一次更新始终只作用于一台主机的一个节点。

## 回滚边界

如果没有数据库迁移，失败时切回旧镜像 digest 并保留数据。若已迁移但尚未开放写入，停止目标版本，恢复升级前完整备份，再运行旧镜像；恢复需重新登录的会话按现有备份规则处理。若 `1.0.0` 已接收写入，不自动用旧备份覆盖数据，也不直接运行不认识新 schema 的旧镜像；执行器停止进一步升级、告警，并等待向前修复或人工恢复决策。界面必须明确显示这一状态，不显示“回滚成功”。

## 必须完成的验收

- 用真实 `0.2.0` 包、持久卷和账号数据演练 `0.2.0 → 1.0.0`，覆盖数据库、附件、节点身份和客户端登录；禁止用空库或同版本重装代替跨版本测试。
- 在 Linux 容器中完成首次启动、备份、校验、隔离恢复、重建容器和整机重启。验证新版本无法启动、下载中断、磁盘不足、备份失败和迁移中断时的状态与恢复。
- 故障注入一项耗时自动备份，在 `running` 期间提交更新任务，确认更新延后且容器不被停止；备份结束后才继续更新。验证心跳失联、状态文件损坏和备份与更新同时抢锁时均安全失败。确认 Compose 的 30 分钟停止宽限期实际生效，不把 Docker 默认的 10 秒当作足够的优雅退出时间。
- 验证旧 Service Worker 页面和 `0.2.0` 桌面客户端的兼容行为；不兼容时明确提示升级并阻止有风险的写入。
- 浏览器与桌面本地 schema 127 的升级另设客户端迁移流程和备份验收；服务器镜像升级不得清理或重置客户端本地账本。
- 三台独立主机上逐节点更新，确认每次重启后副本组重新达到 `READY`、附件承诺与物理校验一致。
- 发布 `1.0.0` 前先提供可信镜像仓库、签名密钥和异机备份位置；发布流水线记录镜像 digest、源码提交、构建 Node 版本及验收结果。

## 实施批次

1. **发布与迁移基础**：镜像仓库、签名清单、版本元数据、schema 27 到目标版本的迁移器及真实旧数据夹具。
2. **主机执行器**：拉取、排空、备份、迁移、启动、验收和回滚状态机；断电重启后可继续报告准确状态。
3. **管理界面**：检查版本、查看说明、执行更新、进度、历史和受回滚边界约束的操作入口。
4. **生产验收**：容器故障注入、隔离恢复、客户端兼容及多主机滚动更新。全部通过后才开放 `1.0.0` 更新入口。
