# 多账本账号迁移设计

浏览器旧加密 SQLite 快照的 `storageId` 是设备缓存密钥 ID，不能用作业务账本 ID。网页刷新时只检查旧快照是否存在，不读取整个加密数据库；由账本密钥封套、设备恢复记录或旧同步连接识别原副本。多服务器浏览器测试覆盖了设备缓存 ID 与账本 ID 不同、刷新后其他服务器连接仍在的情形。

状态：步骤 1、2 的服务端基础及网页账本切换已实施；Windows 桌面端已从实际 WebView2 窗口触发个人与共享账本往返切换并验证重启、独立记账和附件；步骤 3、4、5 仍需完成全部路径及真实三节点验收。步骤 6 的服务端本机三节点演练已验证个人账本与受邀共享账本并存、两站独立会话、身份节点离线时分别写入、恢复后收敛及三节点分别解密核对记录。本机 Chrome 演练进一步覆盖同一账号在公网、家庭、办公三个独立网站进入两本账：个人账本与共享账本各有独立 IndexedDB 缓存和可见记录，个人账本上传极小 PNG，共享账本上传约 5 MiB 的有效 PNG，并从另一站打开预览；共享图片已验证分成多个加密块，两个上传网页关闭后由节点定时后台任务自行复制，新页面在三站均可预览；公网停服期间，办公网页继续向共享账本写入，家庭网页继续向个人账本写入；公网恢复后，两本账的提交和附件目录各自在三节点收敛，公网网页可以读到断网记录。重新进入受控共享账本需要再次解锁成员密钥，在非托管副本进入个人账本需要恢复码。真实设备和真实照片传输耗时仍待验收。`ledger_account_routes.username` 仍是旧接口的默认副本路由；个人账本账号加入受控共享账本不会改写原路由。每个节点会话记录自己的选中副本，选择接口会重发限定该副本的访问令牌，并使旧令牌失效。旧保护与整账本替换接口只允许操作原副本；成员控制启用后，旧保护写入、旧密钥包写入及整账本替换均被拒绝，密钥轮换改走成员控制链。schema 23 为个人账本替换新增事务内加密检查点，恢复时也先保存当前副本；旧附件和备份目录在恢复前保留。旧读路径及存储结构仍待退出。

schema 16 增加 `account_ledger_index` 和会话 `replica_id`；schema 17 增加会话选择版本，schema 18 将服务器备份目录按副本隔离。账号账本索引由签名成员控制链重建，没有成员链的旧账本按原路由回填。`/api/auth/me` 列出可选账本，`/api/auth/ledger/select` 校验成员及当前密钥封套，改变当前会话的副本并重发令牌。提交、成员控制、用量、V2 附件、备份及节点复制授权已按选中副本寻址。身份节点签发的有效成员在节点复制补齐账号密钥和成员封套后可预建目标节点账号；同一联合身份已有个人账本时，联合登录新会话可直接进入受邀账本，原路由不变。同一身份节点对应多个账本链路时，登录入口按链路列出。浏览器按副本隔离本地设置、加密 SQLite、附件缓存与临时凭据；旧 `v2` 空间留给原副本，新副本使用独立 `v3` 空间。网页切换会等待当前同步结束、阻止新同步、关闭旧账本并通知同站其他标签页；桌面端重启切换、独立数据与附件已在真实 WebView2 窗口验收，离线冷启动和隔离副本备份恢复的记录见 `docs/native-desktop-acceptance.md`。旧 V1 附件、未完成上传、旧提交影子表及旧保护接口还需要完成迁移与故障验收。

正常提交、个人账本替换与恢复现在直接写 `ledger_replica_commits`；替换检查点也从该表复制整条加密历史，并核对序号连续性。`sync_server_commits` 保留升级前的历史副本；其旧格式插入只在账本 ID 匹配且目标提交尚不存在时导入，旧行的更新或删除不再改动副本提交。启动时只核对旧表已有的行，当前写入不再继续扩增旧提交分区。旧备份影子结构仍待退出；确认独立备份与迁移回滚后才能移除旧提交表及触发器。

密钥包的日常读取、写入、代次冲突检查和替换前检查点改以 `ledger_replica_key_envelopes` 为准；旧账号密钥包行缺失时，重启、个人账本替换及恢复仍能使用已验证的副本密钥包。旧账号密钥包表与兼容触发器仍为旧版升级和回滚保留；只有账本 ID 匹配且代次更高的旧写入才可向副本表前进，删除旧行不会删除副本密钥包。旧行若落后于副本密钥代次，启动校验允许其作为历史影子，但同代次的不同密文仍会停止启动。确认独立备份后再清理旧表及触发器。

账本最低客户端能力的新写入也只进 `ledger_replica_requirements`。旧账号能力行仅为升级核对保留；迁移和启动校验会先匹配原账本 ID，不能把个人账本替换前的能力误套到新副本。旧行删除或改写不会撤销副本已有的最低能力要求。替换后的重启、无旧能力的新账本写入及旧账本恢复已有回归测试。

停服维护命令 `retire-legacy-shadow` 先制作并校验独立备份，再对照副本权威表核对旧提交、密钥包、最低能力和备份归档；任何旧行没有可证明的权威对应项都拒绝清理。通过后在事务内清空并删除旧表与触发器，将该数据库显式标记为 schema 25；普通启动不会自动把旧数据库升级到 25。可选 `VACUUM` 回收 SQLite 文件空间，临时服务器测试覆盖清理后重启、备份回滚和漂移拒绝。

旧 V1 附件由持有账本密钥的客户端解密校验并上传对应 V2 后，客户端向当前副本登记旧对象与新对象的迁移关系。服务器保留旧 V1 密文及备份可恢复性；只有对应 V2 仍为可用对象时，旧对象才不计入“待迁移”数量。V2 丢失或进入回收站时，旧 V1 会重新出现在待迁移目录与旧账号发现接口中。迁移关系单独保存在 SQLite，不随启动时的附件侧写重建而消失，并记录声明者账号；只读和已移除成员不能登记。V2 上传成功但登记中断时，下一次同步会重新发现 V1、核对已存在的 V2 并补登记。服务器仍无法自行证明两个密文的明文相同，这一声明与附件承诺目录一样依赖已获写入权限的客户端校验。

迁移登记后，附件**逻辑配额**只计算可用 V2，不再把对应的旧 V1 重复计费；V2 不可用时旧 V1 恢复计费。登记之前，上传新 V2 仍要求剩余配额至少能容纳该附件；迁移一批附件时至少预留最大单个新密文的配额空余。旧 V1 密文仍实际占用磁盘，所以节点还需要容纳两种格式及备份的物理空间。配额调整不能代替磁盘空余检查，旧密文也不能在独立备份和可恢复性核对前清理。

## 目标模型

旧 V2 附件对象、删除状态与未完成上传已有启动回填和同副本续传测试；旧 V1 对象仍须由持有密钥的客户端转换。schema 24 将旧账号附件配额回填到副本配额表，旧管理接口在过渡期同时更新两者，附件用量按副本配额判断。启动时只把唯一活动路由或替换检查点能够证明归属的历史对象写回侧写和 SQLite；不能唯一证明的对象、删除状态及暂存上传保留原样。管理后台空间页可分页查看这些记录及其 V1/V2 格式、当前路由和检查点给出的候选副本，并把账本 ID 不匹配的既有副本标记计入未归属数量。服务器所有者可在维护窗口内对单个 V2 对象选择有效候选、填写核对依据并修复归属；操作逐块校验密文，决定写入 SQLite 与对象侧写，重启重建目录后仍可追溯。孤立删除状态也可在维护窗口内人工指定候选副本；服务端会拒绝与现有对象冲突的选择，并保存独立审计记录。V2 暂存上传可以在维护窗口内修复，须核对物理目录、清单和所有已保存分块；修复会延长暂存期限，以便客户端继续上传。任何上传的分块写入都会刷新期限，清理与正在进行的分块写入互斥。修复前须完成独立备份，用原账本密钥核对对象、暂存上传或原始删除操作确属所选副本；服务端只能校验密文字节，无法自行证明密钥或孤立状态的归属。

同一账号与账本若出现多个候选副本，启动修复还会比对 V2 物理目录的副本哈希；能唯一匹配的附件、关联删除状态和未完成上传可自动回填。侧写已记录副本 ID 时也须匹配有效路由或检查点。只有账号旧目录而无其他证据的歧义对象继续留在未归属清单，不会猜测归属。这些空归属对象及上传不会进入任一候选副本的读取、用量、复制或续传路径；原账号再次上传同一对象 ID 时返回归属待核对错误，避免静默覆盖。删除状态若与旧歧义记录撞键，也拒绝以新副本状态覆盖；副本逻辑用量只统计其账本 ID 下的对象与暂存上传。定时清理跳过未归属对象的回收站期限，以及未归属暂存上传的过期时间，保留密文供后续核对；已确认副本归属的记录继续按正常保留期清理。

修复后尚未收到新分块的暂存上传继续跳过到期清理；收到分块后按刷新的期限清理。归属修复记录保存在审计表，暂存上传完成后仍保留。

| 对象 | 稳定主键 | 作用 |
| --- | --- | --- |
| 账号身份 | `(issuer_node_id, subject_account_id)` | 同一人的全局身份；登录密码由身份节点管理 |
| 节点会话 | `session_id` | 只在当前节点有效，携带已选择的 `replica_id` |
| 账本成员 | `(replica_id, issuer_node_id, subject_account_id)` | 由账本签名成员控制链决定角色和有效性 |
| 副本槽位 | `replica_id` | 本节点上的提交、附件、控制数据和密钥封套空间 |
| 账号账本索引 | `(issuer_node_id, subject_account_id, replica_id)` | 登录后列出可选账本；由成员控制链重建，不单独授予权限 |

一个节点会话只选择一个账本，但同一账号可以同时拥有多个会话，各自选择不同账本。每个账本的加密提交和附件都按 `replica_id` 寻址。节点管理员加入新副本时，先创建独立副本槽位；不应自动取得账本成员资格。

## 迁移顺序

| 步骤 | 存储与接口改动 | 必须验证 |
| --- | --- | --- |
| 1（已完成存储基础） | 新增账号账本索引和会话级 `replica_id`，从旧路由及签名成员链回填 | 旧账号登录和现有副本不变；不同账本不合并 |
| 2（已完成服务端与网页基础） | `/api/auth/me` 提供可选账本；选择接口重发限定副本的访问令牌 | 两个独立会话选择不同账本，旧令牌失效；同站标签页切换时锁定旧账本 |
| 3（部分完成） | 账本读写、成员控制、附件、备份和复制授权按会话副本寻址；逐步退出用户名隐式路由 | 改写请求账本 ID 不能越权；角色由当前账本控制链判断 |
| 4（网页基础完成） | 浏览器按账本隔离 IndexedDB、设备缓存、密钥和同步配置；切换时关闭旧同步作业 | 两个账本交替进入、离线恢复、附件上传均不串账；桌面端另行验收 |
| 5（附件、配额与备份目录部分完成） | 旧 V2 对象、删除状态、未完成上传和附件配额已按副本回填；V1 客户端转换、登记和逻辑配额扣重已接入；无归属记录可逐项人工核对并修复，旧提交等影子载荷可在停服、备份并核对后显式退役至 schema 25。仍需用真实旧数据完成全量迁移并退出旧账号路由 | 大账本升级后字节和对象计数一致，备份可回滚 |
| 6（服务端与本机三站网页演练通过） | 允许已拥有个人账本的账号加入共享账本，并在三个副本登录、选择和记账 | 已有个人账本不会被邀请覆盖；本机三站网页在公网停服期间分别向两本账写入并于恢复后收敛，真实设备待验收 |

切换前需要对 SQLite、附件目录和节点身份做独立备份。迁移只增加新表与字段，先双写并核对数量和哈希；旧读路径在新接口通过故障演练后再退出。不能把账号级活动路由用作会话级选择的替代品。

## 桌面端切换前必须补齐的隔离

Windows 便携桌面入口仍直接挂载 `LedgerApp`，但启动前先读取账本 profile。旧账本继续使用原来的 `ledger.sqlite`、附件、备份、安全库和 WebView 目录；新账本使用 `data/ledger-profiles/<profileId>/` 下相互独立的同类路径。切换先暂停同步和自动备份、关闭 SQLCipher 连接并锁定设备与账本密钥，再更新 profile 目录并重启应用；旧窗口的服务器会话仍留在原账本，新窗口登录后再选择并核对绑定的服务器副本、账本 ID 与世代。目标账本登录失败时，锁定页可返回原始本机账本。注册表损坏时启动拒绝退回旧路径。2026-10-10 在隔离的 Windows 调试桌面窗口通过 WebView2 调试端口完成两本账往返切换：个人与共享账本分别记账、重启后各自读取、上传同名图片并分别预览；两个附件密文落在不同 profile 路径且哈希不同，自动备份也分别写入各自目录。停掉测试服务器时，个人账本仍能本地记账；服务器恢复后手动同步，远端提交数从 4 增至 5。首次尝试发现重启扫描 WebView2 临时文件的竞态及新 profile Stronghold 解锁时会话丢失，均已修复并重新走通窗口流程。之后已在真实 WebView2 窗口验收关窗后离线冷启动解锁及隔离副本的备份预检、恢复，见 `docs/native-desktop-acceptance.md`。公网、家庭、办公室三台独立设备仍待实机验收。其他 Tauri 平台暂不开放 profile 切换。

| 顺序 | 桌面改造 | 验收点 |
| --- | --- | --- |
| 1（实窗已验收） | 为每个副本建立稳定的本机 profile；已有单账本文件留在 legacy profile，记录其原始 `replicaId` | 升级后原数据库、附件、备份和密钥仍能打开；新副本不复用 legacy 路径 |
| 2（实窗已验收） | 原生 SQLite、附件、备份、Stronghold 与 WebView 存储按 profile 隔离 | 两个账本同名附件和不同 SQLCipher 密钥互不串用；重启后仍能分别解锁 |
| 3（实窗已验收） | 切换时停止同步、等待自动备份、关闭数据库、清空账本密钥及运行时状态，选择目标 profile 后重新打开 | 旧账本不再写入；切换失败时保持锁定，不退回其他账本 |
| 4（本机实窗已验收） | 对两个账本交替执行记账、离线写入、附件上传、备份与恢复 | 桌面本机两个账本的对象数及密文字节互不混用；三台独立设备仍需实机验收 |

统一身份三节点测试已经覆盖成员在两个局域网网页分别登录、公网身份节点离线时继续使用本地会话并写入、恢复后收敛；旧成员写入的三节点人工合并和签名处置也已覆盖数据层与复制链。它们不能替代桌面文件与 Stronghold 隔离验收。
