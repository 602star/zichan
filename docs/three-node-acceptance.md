# 三节点账本副本实机验收

本清单适用于一台公网中继和两台局域网节点。三台都运行同版本的 `@zichan/sync-server`，各自使用独立、持久的 `DATA_DIR`，并提供自己的 `/app/`。部署、HTTPS 与备份命令见 [cloud-sync.md](cloud-sync.md)。此验收应使用测试账本和可删除的测试账号，不在唯一的生产账本上演练停机与节点退役。

本机自动化覆盖三独立进程、三个 Chrome 网站来源、节点断线写入、恢复追赶、1,203 条提交和 3,000 个 V2 附件。它不能证明真实公网带宽、证书、磁盘持久性、整机重启和局域网路由。本清单用于补齐这些证据。

本机自动化结果仅作为预验收。另有两台物理机器、五个独立逻辑节点的跨机预验收记录，见 [five-node-acceptance-2026-10-28.md](five-node-acceptance-2026-10-28.md)；三台独立设备的公网部署验收仍需单独完成。

## 只有本机时先运行的预验收

在仓库根目录的 PowerShell 中运行：

```powershell
npm run build:server
node --test scripts/three-node-preflight.test.mjs
$env:PLAYWRIGHT_EXECUTABLE_PATH = 'C:\Program Files\Google\Chrome\Application\chrome.exe'
npm run test --prefix tools/e2e -- --config account.config.mjs account-tests/replica-join-ui.spec.mjs account-tests/three-site-replica.spec.mjs
npm test -w @zichan/sync-server -- --run test/three-node-process.test.ts test/three-node-fault-recovery.test.ts test/blob-replica-namespace.test.ts test/node-replication-rescan.test.ts test/replica-readiness-http.test.ts
npm test -w @zichan/sync-server -- --run test/retire-node.test.ts test/replica-group-health-http.test.ts
$env:ZICHAN_REPLICA_STRESS = '1'
$env:ZICHAN_REPLICA_STRESS_BLOBS = '3000'
npm test -w @zichan/sync-server -- --run test/large-three-node-replica.test.ts
```

网页演练分别启动三个独立网站来源和数据目录；管理员通过同步组接口创建和加入节点，用户界面只查看副本状态。三站记账、公网节点断开时继续写入、恢复后的提交目录收敛以及移出节点后的写入封锁已由浏览器脚本覆盖。此前同步组自动建链后可能长期停在 `CATCHING_UP · 1/3`；原因是组内统一账号绑定使用组 ID，而副本目录核对错误地按账本 ID 查找。该问题已修复，验收须要求 `READY · 3/3`。个人账本的附件演练要核对大图分块上传、关闭所有网页后的节点后台复制，以及三站跨站读取。服务端测试覆盖独立进程重启、故障恢复，以及加密备份不会被误算成旧附件。需要更大附件规模时，可运行架构文档中的可选压力演练。多人共享账本不属于当前验收范围。

这些结果是本机预验收。取得三台真实设备后，再按下文记录网络、磁盘、证书和长期运行证据。

三台节点上线后，先从管理员电脑运行只读预检（依次填公网、家庭、办公 URL，可带相同的部署前缀）：

```powershell
node scripts/three-node-preflight.mjs https://public.example.com https://home.example.com https://office.example.com
```

它读取每台的 `/api/health` 与 `/api/ready`，检查节点 ID 和 Ed25519 公钥互不相同、协议能力、Web 与同步开关、部署路径及数据库就绪；核对各节点均为当前 schema 27。输出包含完整公钥，管理员需与各节点可信本机来源逐一核对。它不登录、不读取账本，也不证明三站记账或副本 `READY`。输入节点根地址或部署前缀，不要附 `/app/`。仅本机回环演练可加 `--allow-local-http` 并把第一个地址设为 `localhost`、`127.*` 或 `::1`；真正的公网节点必须使用 HTTPS。

## 部署准备

| 项目 | 验收条件 |
| --- | --- |
| 节点身份 | 三台 `/api/health` 的 `serverId`、`nodePublicKey` 各不相同；重启后保持不变。加入时从各节点可信本机环境核对完整公钥。 |
| 数据目录 | 每台的数据库、节点签名私钥、附件和备份有独立的持久磁盘；备份验证通过，并能在隔离目录演练恢复。 |
| 网络 | 家庭与办公节点能主动访问公网中继；客户端能分别打开三个节点的 `/app/`。配置每条链路时，管理员浏览器须同时能访问公网节点和该局域网节点；可以分别在两个局域网内操作，或使用可信 VPN。公网网站使用可信 HTTPS，反向代理正确传递公共 Host 与 HTTPS 协议；从 HTTPS 网页配置局域网节点时，该节点也应提供可信 HTTPS。 |
| 时间与容量 | 三台时钟已同步；各盘的空余量覆盖原账本、附件、副本追赶和备份。记录实测带宽与账本/附件大小。 |
| 账号 | 公网节点签发测试账本所有者身份；家庭和办公节点各有自己的节点管理员，节点管理员本身不取得账本内容权限。 |

## 按顺序验收

1. **建立副本。** 在公网 `/app/` 创建测试账本和一笔记录。管理员在公网节点的管理后台创建服务器同步组，再分别从家庭、办公节点的管理后台加入；核对各节点身份后关闭浏览器，观察服务端继续追赶。用户在“设置 → 服务器与同步 → 服务器上的账本”只查看副本状态，不在该页面手动建立复制链路。记录各节点从加入、追赶、核验到就绪的时间与错误。
2. **核对完整性。** 在每个网站分别查看本节点状态和整组状态。三台节点的账本 ID、世代、提交目录摘要、附件承诺摘要、节点目录一致；承诺附件缺失数、旧 V1 对象数均为零；本地附件逐块校验通过。全部节点和整组均为 `READY`，报告保持新鲜。只看到某条链路 `READY` 不算整组通过。
3. **三站记账。** 使用同一所有者身份分别登录三个 `/app/`，各记一笔不同金额和描述。刷新并同步三个网站，确认每站都能看到三笔；核对三个服务端的提交数和逻辑目录摘要一致。记录浏览器所连的当前节点及节点后台复制日志，确认其余两站的数据由节点补传。
4. **公网中断。** 停止公网服务或阻断两条到公网的链路。保持家庭、办公站点的既有会话，各新增一笔并同步到本地节点。确认两站仍可记账，而整组健康降级；新的设备在身份节点离线期间不能首次登录属预期限制。恢复公网后，不打开浏览器搬运数据，等待三端提交与附件目录再次一致并回到 `READY`。三个网站应都显示两笔离线记录。
5. **大附件与重启。** 在测试账本上传代表实际照片大小与数量的附件，记录总密文字节、对象数、峰值内存和耗时。复制中分别重启家庭、办公节点，再用原数据目录启动；检查续传游标和已完成块没有丢失或重复占用。最终每站能打开抽样图片，承诺目录和物理块校验通过。用真实预期规模继续运行至少一轮定时重扫。
6. **备份恢复。** 分别创建并验证三台节点的独立备份。在隔离环境恢复一份，检查节点 ID、公钥、账本目录、附件及授权状态；不要把同一节点身份的恢复副本与原节点同时加入副本组。完成后记录版本、时间和恢复结果。
7. **替换并迁出一台旧节点。** 用新节点身份与空数据目录加入替代节点，等待新节点、其余节点和整组状态全部 `READY`，在各网站核对同一组账目和附件，并确认旧节点没有待上传的本地记录。记录此时的完整性证据后，停止旧节点服务，防止它继续接收写入；此时整组会因旧节点失联而降级。从中继将旧节点移出副本组时，接口会要求输入旧节点完整 ID 明确确认。若旧节点误重启并重新连上中继，中继会返回签名移出证明；旧节点会持久封锁该账本写入并显示非 `READY`，其他账本继续运行。旧节点离线时无法即时收到这个证明，仍须先停服并核对待上传记录。再次核对留下的节点和整组达到 `READY`，再使用下述维护命令清理。强制确认不能代替停服前的账目、附件和待上传记录核对。

### 整台旧节点的数据目录清理

此命令清理**整台节点**的数据目录（数据库、节点身份、会话、附件及暂存文件），只接受最多包含一本账且最多一个独立副本槽位的目录；相同账本 ID 下的两份独立历史也会拒绝。有其他账本或副本槽位时先迁出并单独处理。它不联系其他节点，也不能单独证明旧节点没有独有的离线写入。先完成上面的替换、账目与附件核对、移出副本组，再停止旧节点服务及备份监督进程。在旧节点本机运行，明确指定数据目录、备份输出目录和从该节点读取的完整 ID：

```powershell
npm run server:retire-node -- --data-dir D:\old-ledger-node --dry-run
npm run server:retire-node -- --data-dir D:\old-ledger-node --output D:\retired-node-backups\old-node-2026-10-11 --confirm-node-id srv-example-id
```

正式命令会先检查数据库、节点 ID、账本范围和副本槽位，创建并验证位于数据目录外的完整备份，再删除这个指定的数据目录。运行中的服务、备份监督进程、节点 ID 不匹配、目录联接、备份路径与数据目录互相包含、多账本或多个独立副本槽位均会拒绝清理。备份及恢复前保留的 `*.before-restore-*` 目录仍含旧密文，需要按独立保留策略处理；文件删除也不等于磁盘安全擦除。清理后若需重新使用这台机器，必须用全新的数据目录和节点身份加入，不能把旧备份作为新节点同时上线。

### 多账本节点只清理一本账的副本

同机还有其他账本时，先完成上述替换、停服与副本组移出，再预检目标 `replicaId`：

```powershell
npm run server:retire-local-replica -- --data-dir D:\multi-ledger-node --replica-id rep-example-id --dry-run
npm run server:retire-local-replica -- --data-dir D:\multi-ledger-node --replica-id rep-example-id --output D:\retired-replica-backups\rep-example-id-2026-10-11 --confirm-node-id srv-example-id --confirm-ledger-id ledger-example-id
```

预检列出目标账本、其他账本、附件对象与暂存上传数量、待清理的物理命名空间及阻止原因。同一账本 ID 下还有另一独立副本、附件或上传归属不明、或目录被其他账本引用时拒绝执行。正式命令新建并验证整台节点的独立备份，撤销指向目标副本的本地会话，清除该副本的提交、账本密钥封套、节点链路与附件目录；**账号、节点身份和其他账本保留**。若清理在数据库或文件阶段中断，数据目录中的 `local-replica-retirement.pending.json` 会阻止服务启动，须停服后用相同参数续跑；不要手动删除标记。完成后重启节点，实际登录并核对其他账本的提交和附件。独立备份仍包含清理前的全部账本，需单独管理保留期。

## 通过标准与记录

每一步保存节点版本、节点 ID、公钥指纹、站点 URL、开始和结束时间、提交与附件数量、逻辑目录摘要、缺失/拒收数、链路阶段、本节点和整组状态、最近核对时间，以及必要的脱敏日志。不能保存密码、恢复码、私钥、Cookie 或访问令牌。

若任一步未达到预期，保留该节点的数据目录与加密备份，记录具体失败阶段；不要清空副本或强行重置账本 ID。跨机器验收全部通过后，才能把这组三节点称为可互换的生产副本。

若链路长期未收敛，记录操作前后的游标、目录摘要、传输量和状态，再由管理员调查；当前用户副本页只显示状态，管理后台尚无“重扫并补传”入口。服务端重扫能力会保留数据与授权，重新核对并按对象去重补传；若报告节点世代、授权或本地数据损坏，按故障原因处理，不能把重扫当作备份恢复。
