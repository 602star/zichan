### 0.2 核对中新增的事实

- **F1（部署）** Compose 的 healthcheck 打的就是 `/api/ready`，`interval: 30s`（`docker-compose.yml:27-31`）→ 现状是**每 30 秒**对数据库做一次全库级检查，而不是“只在部署时检查一次”。
- **F2（就绪探测）** `/api/ready` 的实现是 `store.verify()` → `PRAGMA quick_check`（`server.ts:777-780`、`store.ts:1360-1375`）。所以：
  - 它不是“深度完整性校验”，真正的 `integrity_check` 目前**并不存在**，后台“校验服务器数据库”按钮（`AdminConsole.tsx:201` → `POST /api/admin/database/verify`）走的是同一条 `quick_check` 路径；
  - 初稿“完整性校验转入维护任务”实际是**新增一项能力**，而非迁移现有能力，措辞需要与实际能力对齐。
- **F3（健康检查）** `/api/health` 每次请求做 5 个 `COUNT(*)`（账号、禁用、邀请、会话）加 `SUM(cipher_bytes)`（`server.ts:736-775` → `store.ts:1277-1300`）。这是 **O(表) 聚合**，不是“读取全量账号与会话”；其中 `SUM(cipher_bytes)` 在百万行提交表上就是全表扫描。管理后台每次打开都会先打它（`AdminApp.tsx:27`、`client.ts:76-87`）。
- **F4（接口规范）** 现有错误响应体是 `{ code?, error }`（`server.ts:1295`），**没有 `requestId`**；能力协商已经有 `capabilities` 数组（`server.ts:739-757`）。新增管理接口必须同时加 capability 标记，否则旧前端会把新接口当旧接口打。
- **F5（权限）** 权限判定目前分散在服务端各 handler（`auth.role === 'owner'` 内联判断、`assertManageTarget`）与前端展示判断（`AdminConsole.tsx:105-106` 的 `manageable`/`quotaManageable`）→ 统一权限矩阵时，前端只能负责“灰掉按钮”，判定必须留在服务端。
- **F6（并发）** 管理端已有可复用的并发保护：`AdminClient` 的 generation 机制会取消并丢弃旧请求（`client.ts:62-74`），`useData(client, path, revision)` 用 `revision` 做刷新失效（`AdminConsole.tsx:37-47`）→ “并发修改检测”应扩展这套机制，不另造轮子。
- **F7（前端结构）** 管理后台**没有路由**：`AdminConsole.tsx:60` 用 `tabs` 状态切面板，`/admin/` 是单页；`apps/web/package.json` 没有任何 router 依赖 → “每页独立 URL”是新增能力，有独立工作量。
  - 好消息：服务端已有 SPA 回退（`server.ts` 的 `serveWeb`：目标文件不存在且**无扩展名**时回退 `index.html`），`/admin/overview` 这类路径可直接刷新；因此**不需要**改服务端，也**不需要** hash 路由，但不能用带扩展名的路径。
- **F8（审计）** 审计表已含操作者、目标、动作、前后值，且与变更同事务提交（`server-admin.md` 会话与审计；`store.ts:888` 附近的 `mutateAdmin`）→ **失败尝试目前不留痕**（事务回滚即消失）。新增失败记录必须走独立事务或独立表，不能挂进会回滚的那个事务。
- **F9（已关闭，2026-09-21）** 方案检查时 `npm run release:check` 因数据库文档落后于代码而失败。`d08060a` 已将文档同步到 version 118 / `current_schema_2026_09_18_account_onboarding`，并记录支持的原地升级路径；本轮复验发布检查通过，无需豁免。
- **F10（门禁盲区）** 现有发布门禁抓不到 F1 之外的这类默认值问题：`scripts/release/check-consistency.mjs:22` 的 `OPEN_REGISTRATION_DEFAULT` 正则要求 `open` 带引号，而 Compose 写的是 `${REGISTRATION_MODE:-open}`，因此**不会被拦住**。改配置时要顺带收紧门禁，否则这次修好仍会回归。
- **F11（备份现状比初稿描述更完整）** 备份已经覆盖：`server.sqlite` + sidecar（`server.secret`、`server-id`、`opaque.server-setup`、`custody.key`）+ `blobs/{objects,trash,staging}` 三个目录（`backup.ts:22-24`、`:210-219`），写入 manifest 逐文件 sha256，并在产出后立刻 `verifyServerBackup`（`:243-275`）；`restoreServerBackup` 恢复时会撤销全部会话、清空未完成登录态与密码重置码（`:278-301`）。→ 所以“不能只复制 SQLite 文件”这个约束**现在已满足**；在线备份缺的是**写协调**（快照与附件保留的一致性），不是“补齐附件”。
- **F12（证据边界）** 本机没有 Docker 与 PostgreSQL。容器内非 root 运行、数据目录权限、旧卷升级（§十 第 7 条）只能由 CI 的 `sync-server-container` job（`.github/workflows/ci.yml`）或目标机演练提供证据；在线一致性备份同理。方案中凡此类条目都写明证据来源，不接受“本机看起来没问题”。

## 一、最终页面结构

采用左侧导航、顶部服务器状态与管理员菜单，移动端折叠导航。页面均有独立 URL，刷新、返回和分享链接不会丢失当前位置。

| 页面 | 主要内容 | 主要操作 | 路由 |
|---|---|---|---|
| 运行概览 | 健康状态、容量、同步趋势、异常、备份情况 | 查看异常、进入相关详情 | `/admin/overview` |
| 用户管理 | 用户列表、角色、状态、配额、保护模式 | 查看详情、禁用、调整配额、密码恢复 | `/admin/users`、`/admin/users/:accountId` |
| 设备与会话 | 所属用户、设备、最近活动、会话状态 | 撤销单个或指定范围会话 | `/admin/sessions` |
| 同步诊断 | 上传/拉取状态、失败原因、客户端信息 | 筛选异常、查看关联请求 | `/admin/sync` |
| 注册与邀请 | 注册策略、邀请列表、使用情况 | 生成、复制、撤销邀请码 | `/admin/invites` |
| 存储与备份 | 空间组成、校验、备份、恢复演练 | 发起任务、查看结果 | `/admin/storage` |
| 任务中心 | 排队、执行中、已完成、失败任务 | 查看进度、取消、重新执行 | `/admin/jobs`、`/admin/jobs/:jobId` |
| 日志与审计 | 运行日志、管理审计两个子页面 | 查询、查看详情、受控导出 | `/admin/logs`、`/admin/audit` |
| 系统设置 | 生效配置、告警规则、版本信息、安全设置 | 保存允许在线修改的设置 | `/admin/settings` |

实现要点：

- 路由用 path（非 hash）。服务端 `serveWeb` 已对无扩展名路径回退 `index.html`（F7），因此**不需要改服务端**；`adminBaseUrl()` 已剥离 `BASE_PATH` 前缀，`/ledger/admin/overview` 同样成立。
- 现状 `/admin/` 自动进入概览。旧 `tabs` 模式可直接删除，不需要兼容旧地址。
- 路由是前端新增能力，需要引入 router 依赖或自实现 `history.pushState` 监听；建议前者，并把筛选条件（关键字、角色、状态、游标栈）序列化进 URL query。筛选条件进 URL，**不保存**重置码等敏感内容。
- 管理后台继续只展示管理信息和必要同步元数据，不增加查看用户明文账本或密钥的入口。

## 二、运行概览：从“统计卡片”变成日常工作入口

现状概览只有六个统计卡片（F1）。建议分为四部分：

| 区域 | 展示内容 | 行为 |
|---|---|---|
| 服务状态 | 正常/降级/维护中、运行时间、服务版本、最后采样时间 | 状态异常可进入原因详情 |
| 核心指标 | 请求量、错误率、响应耗时、成功同步账号数 | 支持近 1 小时、24 小时、7 天 |
| 数据保障 | 磁盘余量、最近成功备份、最近校验、最近清理 | 失败或过期时给出处理入口 |
| 待处理事项 | 超额账号、失败任务、持续同步错误、备份失败 | 每条显示影响、发生时间、下一步 |

具体规则：

- 保留“有效会话”，并继续明确它不代表在线人数（`AdminConsole.tsx:91` 已有这句，别丢）。
- 服务端成功响应拉取，只能表示服务端交付成功；客户端是否应用成功，需要客户端确认。
- 未采集的数据展示“暂无数据”，不能显示为零或正常。
- 默认每 30 秒刷新轻量摘要；后台标签不可见时暂停轮询（`document.visibilityState`）。
- 刷新失败保留上一次成功数据，同时标注“数据已过期”。
- 初期只展示已有观测数据，历史趋势从上线后开始积累。
- 轻量摘要走新接口 `GET /api/admin/overview`，**不复用** `/api/health`；后者按 R2 收敛为常量响应。

## 三、用户管理：围绕一个用户完成处理

用户列表建议保留以下列：用户名、角色、启用状态、保护模式、容量使用率、最近成功同步、最近登录、操作。

- 用户名和完整 accountId 搜索继续保留（服务端 `listUsers` 已支持）；增加保护模式、配额状态筛选。
- 分页使用服务端游标（沿用 `limit`/`cursor` + `nextCursor` 约定），筛选条件进入 URL，不保存重置码等敏感内容。
- 列表页提供“详情”入口后，原“设备与配额”内联面板（`AdminConsole.tsx:126-155`）拆分为独立详情页。

用户详情分成五个区域：

| 区域 | 内容 |
|---|---|
| 账号信息 | accountId、创建时间、角色、状态、托管/私密模式 |
| 容量与配额 | 提交、附件、暂存上传、回收站占用及计费口径 |
| 设备与会话 | 当前有效、已撤销、已过期会话 |
| 同步情况 | 最近上传、拉取、失败原因、客户端版本 |
| 操作记录 | 该用户相关审计和维护任务 |

操作流程需要明确：

- **禁用账号**：展示将撤销的会话数量，填写原因，确认后更新状态。
- **调整配额**：显示当前用量、旧上限、新上限；低于现有用量时明确“保留已有数据，限制后续上传”。现有配额输入校验（1 MiB – 1 TiB）与“读取失败前禁用保存”继续保留（`AdminConsole.tsx:140-152`）。
- **修改角色**：重新验证身份（现有“最近 5 分钟内登录”窗口），显示权限变化；完成后撤销目标会话。
- **密码恢复**：保留人工核实、一次性显示、到期隐藏机制；增加“撤销未使用重置码”。
- **并发修改**：提交携带数据版本；其他管理员已修改时提示刷新，不静默覆盖（复用 F6 的 generation + `revision` 机制，升级为服务端版本字段）。

Owner/Admin/Member 权限继续沿用。额外的只读运维角色放在 E 阶段，先把现有权限在页面、接口和任务执行中统一起来（F5、R9）。

## 四、设备与会话：修正管理单位

当前设备列表按账号分页，再展开该账号全部会话，单页设备数量并不固定（F1 核实项）。

建议改为按会话分页，提供：

- 用户、设备名称、会话类型、有效状态、最近活动时间筛选。
- 区分管理后台会话与记账会话（两种 Cookie 与两套会话，见 `server-admin.md`）。
- 显示首次登录、最后活动、到期时间和来源 IP。
- 支持撤销单会话、撤销指定用户全部可管理会话。
- 批量操作前明确范围，并逐项报告成功、失败和无权限项。
- 保留现有保护：所有者会话受保护，不能被管理员撤销（`server.ts` 的 `parts[0] === 'sessions'` 分支与 `assertManageTarget`）。

不通过 IP 推断精确地理位置；设备名称与客户端版本标记为客户端上报信息。

所有者对自己的会话管理需要单独设计：允许重新验证后撤销其他会话，当前会话通过退出结束，避免误操作造成不清楚的登录状态。

## 五、同步诊断：让“同步不了”有迹可查

新增诊断列表，聚合必要元数据：账号、设备、服务端接收时间、操作类型、提交数量、传输字节、耗时、结果代码、请求 ID。

错误分类建议统一：

| 类型 | 页面解释 | 下一步 |
|---|---|---|
| 会话失效 | 此设备登录已过期或被撤销 | 用户重新登录 |
| 配额不足 | 新提交或附件超过可用容量 | 调整配额或由用户整理数据 |
| 协议不兼容 | 客户端版本不支持当前协议 | 更新客户端 |
| 账本绑定不匹配 | 当前设备与服务器绑定不一致 | 查看绑定信息及用户端恢复流程 |
| 服务端存储异常 | 数据库或磁盘操作失败 | 查看关联日志和存储状态 |

约束：

- 不能把长时间没有同步直接判定为故障：用户可能离线或没有新操作。
- 服务端看不到的客户端离线失败，只有新增客户端诊断上报后才能展示；这部分必须明确标记覆盖范围。
- 后台不提供“强制重新同步所有用户”这样的操作。
- 诊断数据来自运行日志与新增诊断事件表；日志已有按时间和大小裁剪（见 §十 第 5 条），诊断事件需要**独立保留策略**，不能被日志裁剪带走。

## 六、任务中心：把耗时操作从 HTTP 请求中移出来

附件校验目前在请求内循环同步读取文件并计算哈希（F1 核实项），应优先改造。

统一任务状态：`排队中 → 执行中 → 成功 / 失败 / 已取消 / 执行中断`。

每个任务记录：

- 任务 ID、类型、发起人、目标范围、创建时间。
- 开始/结束时间、阶段、已处理数量、总量或已扫描数量。
- 结果摘要、错误代码、关联日志。
- 是否允许取消、重新执行以及原任务 ID（`retry_of`）。

执行规则：

- 首期重型维护任务最多同时执行一个。
- 分批扫描；文件读取和哈希放到独立工作线程或进程，避免阻塞 HTTP 服务。
- 创建任务返回 `202 + jobId`，页面查询进度。
- 刷新或关闭页面不影响任务。
- 服务重启后识别失去执行者的任务，标记中断；只有已实现检查点的任务才自动续跑。
- 取消在安全边界生效，不强杀正在提交的数据库事务（置 `cancel_requested`，执行器在批次边界检查）。
- 重新执行创建新任务，保留原失败记录。
- 执行前重新检查操作者权限；已被撤销权限的排队任务不继续执行。

**任务边界（R6）**：后台可发起的任务只包含不触碰生产数据目录的有界工作——数据库深度校验、附件校验、回收站/暂存清理、指标与日志维护、恢复演练。停服备份与生产恢复继续由部署侧维护程序执行（`apps/sync-server/src/maintenance.ts` 的 `backup|verify-backup|restore|owner-recovery`），后台只登记结果与展示，不提供接口去调用一个必须先停掉自身的流程。

现有两个同步 POST 需要改造：`POST /api/admin/database/verify` 与 `POST /api/admin/quotas/blobs/verify`（`AdminConsole.tsx:201-202`）改为创建任务并返回 `202`。

## 七、存储与备份：必须补齐完整恢复流程

存储页分别显示：数据库、WAL 文件、有效附件、回收站、暂存上传、备份目录的占用，以及磁盘可用空间。

逻辑配额占用与物理磁盘占用分开显示，并说明哪些项目计入用户配额。现有定时清理失败不能继续静默吞掉（F1 核实项），应记录最近运行、成功、失败和释放空间。

备份按两个步骤建设：

**第一步：把现有停服备份做成可管理流程。**

现状：`createServerBackup` 要求服务已停（依据 `server.pid`），备份范围已包含数据库、密钥 sidecar 与附件三个目录，产出后立即校验（F11）。

- 用部署侧维护程序执行“停止服务 → 备份 → 校验 → 恢复启动”。
- 后台展示计划、维护窗口、执行记录和校验结果。
- 后台不直接调用一个必须停掉自身才能完成的流程。
- 桌面内置服务、Windows 服务和容器部署分别接入对应启动管理方式。
- 自动备份默认不启用；配置备份位置和维护窗口后才能启用。

**第二步：设计在线一致性备份。**

在已有全量备份基础上（R7），要使数据库快照、附件对象、回收站和密钥文件属于同一可恢复状态，需要实现写入协调（快照期间冻结/排队写入或标记代次）与附件保留机制；不能只复制 SQLite 文件，也不能声称支持在线备份而不做这两件事。

备份记录包含：版本、创建时间、文件数、总大小、校验状态、最近恢复演练结果。

特别处理现有备份中的认证与托管密钥：

- 备份目录不由 Web 静态服务暴露（`serveWeb` 只服务 `WEB_DIST`，需确认备份目录不在其中，并加启动校验）。
- 首期不提供浏览器下载整套服务器备份。
- 异地备份需要单独加密，解密凭据与备份分开保管。
- 保留策略仅清理已经校验成功的历史备份，并至少保留最近一个有效备份。

恢复演练在隔离目录执行（独立 `DATA_DIR`）：验证清单、数据库、附件引用、服务启动及旧会话撤销。恢复生产数据继续走部署侧受控流程（`restoreServerBackup` 会把替换前数据目录改名为 `*.before-restore-*` 保留）。

## 八、日志、审计和告警

运行日志与管理审计使用不同的展示和保留规则。

| 项目 | 运行日志 | 管理审计 |
|---|---|---|
| 目的 | 排查错误和性能问题 | 追溯权限、账号、配置变更 |
| 主要字段 | 请求 ID、路由模板、耗时、结果、错误代码 | 操作者、目标、动作、原因、前后值 |
| 失败处理 | 有降级输出，避免日志故障放大业务故障 | 关键管理变更写审计失败必须回滚 |
| 保留 | 按时间和大小限制 | 独立保留与归档策略 |

当前事务审计必须保留。新增失败操作记录时，不应混入已经回滚的事务，而是单独记录失败尝试（F8、R8）——落点建议：`mutateAdmin` 失败分支用独立事务写一张 `admin_audit_failures` 表（或同表加 `outcome` 字段但明确它不属于事务审计）。

审计界面默认显示可读文本，例如：

> 管理员李四将用户张三的附件配额从 2 GiB 调整为 5 GiB。原因：容量申请。

原始字段放到详情。支持时间、操作者、目标用户、动作筛选及受控导出；不导出邀请码、重置码、令牌和密钥。

告警首期在后台展示，规则建议：

- 容量达到配置阈值。
- 备份失败或超过预期时间未成功。
- 校验发现问题。
- 清理任务连续失败。
- 持续出现同步服务错误。

同类告警合并，记录首次发生、最后发生、次数、确认人和恢复时间。需要连续异常才触发，恢复也要验证，避免状态反复跳动。外部邮件或其他通知渠道作为可选配置。

## 九、接口、数据与工程设计

建议新增以下接口，现有账号管理接口逐步复用统一组件：

| 接口 | 用途 |
|---|---|
| `GET /api/admin/overview` | 轻量运行摘要 |
| `GET /api/admin/metrics` | 指定时间范围的聚合指标 |
| `GET /api/admin/accounts/:id` | 用户详情 |
| `GET /api/admin/sessions` | 按会话分页 |
| `GET /api/admin/sync-events` | 同步诊断查询 |
| `POST /api/admin/jobs` | 创建允许的维护任务 |
| `GET /api/admin/jobs/:id` | 查看进度和结果 |
| `POST /api/admin/jobs/:id/cancel` | 请求取消 |
| `GET /api/admin/backups` | 备份记录 |
| `GET /api/admin/alerts` | 告警列表 |
| `GET /api/admin/settings` | 脱敏后的生效配置 |

统一约定：

- 错误响应包含 `code`、可读说明和 `requestId`；现在只有前两项（F4、R5）。`requestId` 要同时进运行日志，页面错误提示里能直接给用户报这个号。
- 新增能力加 `capabilities` 标记（如 `admin-console-v2`），旧前端见到缺失标记时降级到现有行为，而不是打到新接口。
- 分页参数和日期范围在服务端验证，时间统一存 UTC。
- 新增写接口支持幂等键；同键不同参数拒绝，同键相同参数返回同一次操作结果。幂等记录要有保留窗口与上限，不能无限增长。
- 所有目标资源均在服务端做权限检查（F5、R9）。
- 耗时任务不允许传入任意命令或文件路径，只接受预定义任务与参数。
- 系统设置采用允许修改的字段清单，密钥仅返回“已配置/未配置”。
- 环境变量覆盖数据库设置时，页面显示配置来源和实际生效值。

建议增量添加任务、备份记录、指标分桶、诊断事件、告警状态、幂等请求记录等表。审计表扩展请求 ID、操作原因；时间、目标用户和动作增加适合查询的索引。指标与诊断数据需要各自的保留期（例如指标分桶 1 分钟粒度保留 7 天、1 小时粒度保留 90 天），并考虑 `journal_mode = WAL` + `synchronous = FULL` 下高频采样写入的代价。

拆分现有服务代码时，按认证、账号、管理、同步、附件、维护组织（现在 `server.ts` 1261 行、`store.ts` 1317 行是单文件承载全部）；前端按页面拆分，抽取表格、筛选、详情和操作反馈组件。继续使用模块化单体和 SQLite。

## 十一、实施顺序与交付标准

| 阶段 | 交付范围 | 完成标准 |
|---|---|---|
| A：可靠性基础 | 默认配置（第 1、3、5、6 条）、轻量健康/就绪探测、清理异常、接口错误规范 | 不改变既有账号与同步行为，新增异常可观测 |
| B：后台工作流 | 路由与独立 URL、用户详情、会话分页、可读审计、重新验证 | 刷新保留页面和筛选；权限、冲突、失败反馈完整 |
| C：维护与数据保障 | 任务中心、异步校验、备份记录、停服编排、恢复演练 | 中断有记录、重复请求不重复创建任务、备份可恢复 |
| D：运行管理 | 指标、同步诊断、告警、日志关联、配置页 | 能从概览异常追到用户、请求或任务，并验证恢复 |
| E：增强 | 管理员 MFA、归档策略、性能优化（第 2、4、7、8 条收尾） | 恢复路径和权限测试通过，达到约定容量目标 |

阶段验收不能只检查“页面能打开”，还应覆盖：

- Admin 不能通过直接请求管理受保护账号。
- 页面退出或账号切换后，旧请求不能填回数据。
- 两名管理员并发修改能识别冲突。
- 请求超时后可核实结果，不重复发码或创建任务。
- 校验大量附件时，登录与同步仍可响应。
- 服务在任务中退出，重启后不把中断任务显示为成功。
- 磁盘不足、权限不足、附件损坏时显示明确错误。
- 恢复备份后旧会话和已消费恢复凭据不重新生效。
- 已有用户、角色、配额、账本绑定、托管/私密模式在迁移后保持正确。

性能验收先记录基线，再在固定机器与隔离测试数据上验证；覆盖例如 100/1,000 个账号、10 万/100 万条提交，以及较多小附件和较少大附件两种负载。最终容量承诺依据测量结果确定。

范围建议按 **A–D 作为完整后台一期，E 作为增强阶段**。公网多人使用时，将管理员 MFA 提前作为上线条件。

## 十二、边界与不做的事

- 不新增查看用户明文账本、密钥、密码或恢复码的入口；管理身份不等于账本解密权限。
- 不在后台提供清库、删除账号、远程停服、数据库替换。
- 不通过 IP 推断精确地理位置；设备名与客户端版本标记为客户端上报。
- 不为“长时间未同步”直接判故障；不提供“强制全部用户重新同步”。
- 首期不提供浏览器下载整套服务器备份；不把备份目录挂进 Web 静态服务。
- 不在后台发起必须先停服才能完成的操作；生产恢复仍由部署侧受控执行。
- 不为了性能优化擅自改变现有账号、同步、加密协议行为；A 阶段以“零行为变化 + 新增可观测”为准。
- 不复用 `/api/health` 承载后台统计（R2）；不引入第二个数据库或外部服务（继续模块化单体 + SQLite）。

- 同批次落地“运行日志不能导出”：`GET /api/admin/logs/export?format=json|csv`，沿用页面筛选、最多 5000 条，并新增按字段名与取值形态两条独立规则的脱敏（`log-redaction.ts`）——秘密落进自由文本字段时按字段名是挡不住的。
