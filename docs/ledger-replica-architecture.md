# 个人账本与多节点副本

当前产品中，一个账本只属于一个账号。同步组中的多台服务器可以保存该账本的加密副本；节点管理、复制授权和副本组成员均指服务器节点，不代表账本的多人访问权。

## 节点和身份

主节点登记附属节点，使用 Ed25519 节点身份签发复制授权。每个节点保留独立的 `serverId`、数据目录和 SQLite 数据库。账号的 OPAQUE 登录凭据可由身份签发节点经签名目录传递，便于同一账号在其账本所在的节点登录。账号目录本身不赋予其他账号账本读写权。

每个账本副本有 `ledgerId`、`replicaId` 和 `streamEpoch`。服务器根据当前账号的账本路由和会话选择副本。不同节点的 `replicaId` 可以不同，但账本 ID、加密提交及附件目录必须收敛。已有本地提交、附件或删除状态的目标副本不会自动与远端账本合并。

## 复制和完整性

节点使用签名请求双向分页复制加密提交、账本密钥封套、V2 附件、附件删除状态和附件承诺目录。服务器不持有提交明文。提交目录哈希按提交 ID、账本 ID 和内容哈希计算，不依赖节点本地序号或重新加密后的密文。

后台会比较节点间的逻辑提交、账本能力、密钥封套、附件承诺、可用附件和删除状态。每个节点还逐块校验本地附件密文。缺失对象可从健康节点补传；损坏对象进入隔离区并在补传后重验。只有本地目录、物理附件和已启用链路的证据均通过，副本才标为 `READY`。整组健康状态由近期签名报告汇总，仍需在真实三节点设备上验收。

链路状态依次为 `JOINING → BOOTSTRAPPING → CATCHING_UP → VERIFYING → READY`。撤销授权和移出副本组会停止相应节点的复制；已移出节点不得继续写入该副本。

## 数据格式

服务端当前结构为 schema 27，只从空数据目录初始化。多人账本使用的账号加密公钥包、签名成员控制链、每成员密钥包、提交密钥代次和过期成员写入隔离表已删除。schema 26 及更早数据库不会自动升级；旧备份也不能直接作为当前结构恢复。部署时需使用新数据目录。

部署与完整性检查见 [cloud-sync.md](cloud-sync.md)，真实三节点验收见 [three-node-acceptance.md](three-node-acceptance.md)。
