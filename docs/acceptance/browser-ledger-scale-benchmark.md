# 浏览器大账本性能基线

2026-10-20，在 Windows 上用 Chrome 155 无头模式测得。运行命令：

```powershell
node tools/e2e/browser-ledger-scale.mjs 1000,10000,50000,100000,200000
```

脚本会启动本地 Vite 页面，逐档创建隔离的 IndexedDB 账本并在完成后删除。每条 SQLite 测试记录包含约 200 字节的正文；批量填充后，对同一行执行一次预热和五次单行事务写入。写入经过真实的 sql.js 整库导出、加密和 IndexedDB 保存。重新打开计时包括读取、解密、sql.js 加载及一次计数查询。备份测试使用相同条数的合成交易，经过真实的加密归档生成和 `openBackupArchive` 解析，但不执行导入账本。

| 记录数 | SQLite 文件 | 单次写入中位数 | 加密和保存中位数 | 重新打开 | 备份归档 | 生成归档 | 解析归档 | JS 堆抽样高水位 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.21 MiB | 1.4 ms | 0.9 ms | 2.0 ms | 0.53 MiB | 13.9 ms | 91.4 ms | 23 MiB |
| 10,000 | 2.07 MiB | 9.2 ms | 8.3 ms | 7.4 ms | 5.27 MiB | 109.5 ms | 659 ms | 83 MiB |
| 50,000 | 10.31 MiB | 45.8 ms | 42.5 ms | 33.3 ms | 26.37 MiB | 537.8 ms | 2.92 s | 292 MiB |
| 100,000 | 20.62 MiB | 92.3 ms | 86.1 ms | 70.5 ms | 52.74 MiB | 1.05 s | 5.78 s | 473 MiB |
| 200,000 | 41.23 MiB | 187.2 ms | 173.7 ms | 121.5 ms | 105.59 MiB | 2.08 s | 11.61 s | 540 MiB |

这里的“JS 堆抽样高水位”是每 20 ms 和各阶段结束时读取 `performance.memory.usedJSHeapSize` 的最大值，作为峰值的**下界**。它没有计入 WASM、浏览器进程和 IndexedDB 的内存，也可能漏掉阶段内部的瞬时峰值。要得到可用于设备内存预算的峰值，还需在目标浏览器和移动设备上采集进程内存曲线。每档只跑了一轮，延迟需在目标设备上重复测量后再确定产品阈值。

## 影响与方案评估

- **写入：** 测试中单行修改的延迟随整库大小明显增长。约 5 万条时中位数已接近 50 ms，10 万条接近 100 ms，20 万条达到 187 ms；即使修改一行，也要重新导出并加密全库。优先对真实账本记录耗时分布，再验证页级或日志式的增量持久化。方案必须维持加密完整性、原子提交、崩溃恢复和多标签页互斥；简单地只保存变更行无法直接替代当前加密快照。
- **恢复：** 20 万条合成交易的归档解析约 11.6 秒，JS 堆抽样高水位达到 540 MiB，且当前解析器在分批解密和暂存后仍构造完整数组。流式恢复需要把“解密、验证、分批写入暂存库、核对清单、原子切换”串成一条管线，并让导入接口逐批消费记录。仅把读取块调小不会消除最终数组的内存占用。
- **适用边界：** 合成记录没有附件、复杂索引分布、同步、UI 刷新或其他账本实体；不同记录宽度和设备会改变绝对数值。本基线适合判断增长趋势和比较后续实现，不代表线上账本的服务等级承诺。
