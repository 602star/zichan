# 独立服务器管理后台

> 当前账号保护采用[云端托管与私密模式](ledger-protection.md)：托管账号登录后自动解锁，私密账号使用恢复码。最新验收见[交付记录](release-readiness.md)。


新版用户入口以 [Web 账号 v2](web-account-v2.md) 为准：不再兼容旧浏览器本地账本，按账号隔离缓存，用户端不再提供服务器管理页面或跳转。

## 入口与初始化

同一服务器提供 `/app/` 记账应用和 `/admin/` 管理后台。设置 `BASE_PATH=/ledger` 后，入口分别为 `/ledger/app/`、`/ledger/admin/`。需要同站 Web + API 部署，远程访问默认使用可信 HTTPS；显式设置 `ALLOW_INSECURE_HTTP=1` 后可改用私有局域网明文 HTTP。

首次打开 `/admin/`，在 Web 引导中设置管理员用户名和密码即可，不再要求读取或填写初始化密钥。没有内置 admin 用户或默认密码。已有所有者直接登录，不重新初始化；初始化写入为原子操作，只允许一个所有者创建成功。新部署请先完成此设置，再对外开放服务。旧版自动化的密钥接口暂时兼容，但不是 Web 初始化的前置条件。

普通管理页面不经过 StoreProvider，不打开用户账本或申请账本磁盘文件权限。管理员显式打开托管账号的只读预览时，需填写原因并通过服务端权限与最近登录校验，操作写入管理审计；私密账号不能通过后台预览。

## 日常使用路径

导航按总览、用户与访问、数据与备份、运行与维护、事件与记录、系统设置分组。桌面侧栏与手机导航直接显示所有页面入口；个人账号安全位于顶部。

- 先看总览的服务状态和待处理事项，再进入关联用户、备份、任务或日志；技术指标与维护操作直接显示，页头链接可定位到各分区。暂停通知、标记已知晓不代表故障恢复。
- 处理用户问题时先看用户详情顶部的支持摘要，再进入已带账号筛选的同步、会话和审计页面，或打开只读记账预览。
- 存储与备份分别展示计划、最近执行、成功与校验证据。自动执行器尚未提供心跳，运行状态显示未知；清理和演练不算新备份成功。
- 系统设置按用途分组，先核对本组变更再保存；其他组草稿不会一并提交。环境变量覆盖的项需在部署环境修改。

已交付范围和后续模块的验收条件见[后台优化路线图](admin-experience-roadmap.md)。

**只读运维（Viewer）** 是标记为只读的管理员（grant 上的 `read_only` 标志，不是新表）：它能看全部页面并导出日志与审计，但任何管理变更都被服务端拒绝（错误码 `READ_ONLY_ROLE`）；页面也会把写操作控件置为不可用并在顶部说明角色，而不是让人靠“被拒绝”猜出来。管理员可以像管理其他管理员一样**查看**只读运维，但只有所有者能修改它（与“管理员不能管理特权账号”一致）。

需要**最近 5 分钟内登录**的操作：修改角色、发放密码重置码、启用/禁用账号、撤销其他账号的全部会话，以及撤销自己账号的其他会话；刷新访问令牌不延长该窗口。过期时需退出后台、重新登录再操作。角色变更撤销目标现有全部会话；禁用账号同样立即撤销会话，但保留数据。启用账号不复活旧会话。

任务在**开始执行前**再校验一次发起人权限：排队期间被降权、禁用或删除的发起人，其任务会被标为已取消并说明原因（`ACTOR_NOT_PERMITTED`），而不是继续执行。

新服务器默认仅邀请注册，Node、Docker、Windows 启动脚本及桌面内置服务器一致；已有数据库中的注册策略保持不变。Windows 脚本保留显式环境变量覆盖。


## 管理员两步验证（TOTP）

管理后台的登录可以再上一层：账号密码通过后再输入验证器里的 6 位验证码。密钥、恢复码和状态都只属于账号本人——这是**唯一**没有任何角色可以代他人操作的管理变更，`mutateAdmin` 会直接拒绝（错误码 `PROTECTED_ACCOUNT`）。

- **绑定是两步的**：`POST /api/admin/mfa/enroll` 生成密钥并返回一次（含 `otpauth://` 链接，可直接导入验证器），此时**还不生效**；`POST /api/admin/mfa/confirm` 用验证器当前验证码确认，才真正启用并返回 10 个一次性恢复码。半途中断的绑定不会拦住登录——否则唯一的管理员会被自己锁在门外。
- **密钥加密存储**：`server.secret` 派生密钥对 TOTP 密钥做 AES-256-GCM 加密后入库；拿到数据库副本但没有 `server.secret` 得不到可用验证码。恢复码只存 SHA-256 哈希，用一个消一个（数据库副本不会泄露可用的恢复码）。
- **一个验证码只能用一次**：登录成功后记录已消耗的时间步，同一个时间步内的验证码不能再用（允许前后各一个时间步的时钟偏差）。挑战本身也是短时、一次性、限次数的：5 分钟有效期，连续 5 次错误后作废；挑战标识与令牌分两段返回，只拿到其中一半无法使用。
- **恢复码是备用门**：忘记验证器时用一枚恢复码登录（同一输入框），用掉即失效，登录后在「账号安全」页重新生成一批。恢复码用完时会明确提示——此时若设备丢失只能靠部署侧的本地维护程序找回访问。
- **只保护管理后台登录**：同一账号在本机记账端的登录**不要求**验证码（记账入口没有输入第二步的交互，把验证码变成必需项只会让人丢掉账本访问权）。本地维护程序（所有者恢复）同样不要求验证码——那是需要服务器文件系统访问权限的应急路径。
- **`/admin/security`（账号安全）** 是自助页：绑定、确认、查看剩余恢复码数量、重新生成恢复码、关闭两步验证都在这里；页面只在生成的那一刻展示密钥与恢复码，之后不再返回。所有者还能在同一页看到**尚未启用**两步验证的管理员名单。
- **强制要求是可选策略**：`ADMIN_REQUIRE_MFA=on`（或设置页的「要求管理员启用两步验证」）会让管理后台登录必须带已验证的两步验证。开启前会先检查名单：只要还有管理员没有绑定，保存就被拒绝（`MFA_ENROLLMENT_INCOMPLETE`）并列出名字；开着的时候也不能关闭自己的两步验证（`MFA_POLICY_ENABLED`），否则下一次登录立刻进不来。没有绑定的管理员登录会得到 `MFA_ENROLLMENT_REQUIRED`（403），与“密码错误”区分开，避免反复试密码。
- **不会因为策略而启动失败**：策略与某个账号的绑定状态不一致时服务照常启动，登录时才拒绝——把一次登录麻烦升级成一次停机是不划算的。

登录时序：`/api/auth/login/finish` 验证密码后，若该账号需要第二步则**不创建会话**，只返回 `{ mfaRequired: true, challenge, expiresAt, methods }`；`/api/auth/login/mfa` 用 `{ challenge, code, deviceId, deviceName }` 换会话。挑战只在管理后台上下文（`X-Zichan-Session: admin-cookie`）签发与应答，记账登录拿不到也不需要它。两步验证的绑定、关闭与恢复码重新生成都会写入管理审计（`mfa-enroll` / `mfa-disable` / `mfa-recovery-codes`），并需要最近 5 分钟内的登录。

## 管理员自助修改密码

管理后台的「账号安全」页可以直接改自己的账号密码，**不新增服务端接口**：它复用记账端已在用的同一条链路（当前密码经 OPAQUE 重新验证 → `POST /api/auth/password-change/authorize` 取一次性授权 → 用重置码走密码重置提交新密码）。一处服务端规则，两个入口，规则不可能各说一套。

- **当前密码必须重新证明**：控制台会话只能说明「有人在这个浏览器上登录过」，回答不了「现在敲键盘的人知不知道当前密码」。所以页面要求输入当前密码，并用它换一个**一次性令牌会话**去授权——绝不复用控制台的 Cookie 会话。
- **为什么必须用一次性会话而不是控制台会话**：登录会覆盖 `zichan_admin_session` Cookie，若拿它做验证，当前密码输错一次就会把操作者悄悄踢出后台，且看起来像会话无故失效。
- **第二因子只保护管理后台登录**，不保护这条链路：记账形态的登录刻意不要求验证码（否则丢了验证器就丢了改密能力），这条链路与记账端完全一致，页面因此不显示验证码输入框。
- **改密成功即全部会话失效**（服务端在提交新密码的同一事务里撤销该账号所有会话），包括当前这个控制台。所以成功后控制台回到登录卡片并说明原因，而不是留着一个已死的会话让下一次点击失败。
- 改密失败（当前密码错误）**不会**结束控制台会话：错误显示在页内，操作者可以改错别字重试。授权与提交都写入管理审计（`password-change-authorize` / `password-reset-complete`），且不记录授权码本身。

## 注册与用户增长

指标只统计请求维度，「这个月靠哪批邀请码拉来多少人」原本没有任何地方能回答。注册与邀请页因此多了「注册与邀请增长」面板，数据来自 `GET /api/admin/registration/growth`（`range=30d|90d|365d|all`，一年与全部默认按月分桶，其余按日；非法值 400）。

- **新账号**按账号自己的注册时间分桶，桶是 UTC、页面按本地时间显示。「其中来自邀请」是邀请码里记着这个账号的那部分——那是账号与「怎么进来的」之间**唯一存在的联系**。
- **「无邀请码」是一个差，不是一个类别**：它同时包含开放注册进来的账号与部署创建的所有者账号，数据里没有区分这两者的字段，所以页面不假装能区分。
- **邀请码状态汇总覆盖全部历史**，按日期列出的批次只覆盖所选范围。两者刻意分开：汇总回答「邀请码一共拉来多少人」，范围只用来收窄批次表。状态口径与邀请列表页完全一致（可用/已用/已撤销/已过期），否则两处会对同一个码给出不同说法。
- 邀请码本身不在这个面板里逐条列出（那是邀请列表的事）；批次表只回答「那天发了多少、用了多少」。

## 页面与路由

管理后台是独立的单页应用，每个页面都有自己的 URL；刷新、返回/前进和分享链接都会回到同一个页面与同一组筛选条件。筛选条件写入 URL query，不保存重置码等敏感内容。服务端已对无扩展名路径回退 `index.html`，所以路由不需要改服务端，也没有给 Web 包引入路由依赖。`BASE_PATH=/ledger` 时前缀同样生效（`/ledger/admin/users`）。旧的单页 tab 界面不再保留，也不需要兼容旧地址。

| 页面 | URL | 内容与操作 |
|---|---|---|

### 列表的排序、每页条数与列显隐

可排序的列表都支持**服务端排序**、**每页条数**与**列显隐**。用户管理、设备与会话、任务中心、同步诊断、存储与备份（备份记录）、运行日志、管理审计、注册与邀请各自列出自己可排序的列，点表头即按该列重新查询（同一列再点一次反向）；每页条数写入 URL，列显隐记在浏览器本地。

- **排序一律在服务端执行，不在浏览器重排当前页**。只重排屏幕上这 25 行，会得到一份看起来对、实际错的结果——它会被当成“最新的账号”。排序状态通过表头单元格的 `aria-sort` 暴露，排序按钮的可访问名就是列名本身（不额外加 `aria-label`，否则会与同名的筛选下拉冲突）。
- **游标跟着排序键走，并记住自己属于哪个排序**。游标形如 `sort~dir~值|唯一键`；用另一个排序下的游标翻页会被拒绝（`CURSOR_SORT_MISMATCH`）而不是被重新解释——重新解释会返回稳定、看似合理但错误的页。无法解析的游标报 `INVALID_CURSOR`，不会静默退回第一页。旧格式 `值|唯一键` 仍被接受，含义等同默认排序。
- **每列都自带 NULL 安全与类型信息**：可空列在排序表达式里 `COALESCE`，数值列（容量占用、有效会话、文件数、总大小、耗时、提交数量）标为数值型，游标值会转回数字——SQLite 先按类型再按值比较，`12345 > '9999'` 为假，否则第二页会静默为空。
- **时间戳按存储格式比较**：`expires_at` 等是带 `T` 的 ISO 字符串，而 `datetime('now')` 用空格分隔；`T`（0x54）排在空格（0x20）之后，同一天内已过去的时刻会被判成仍未到期。因此时间比较统一用 `strftime('%Y-%m-%dT%H:%M:%fZ','now')` 生成同格式的值。
- **邀请码本身不可排序**：该列表的游标刻意不携带邀请码（分页 URL 会进浏览器历史、Referer 和聊天记录），可排序列是创建时间、有效期与状态；排序与筛选共用同一段状态判定 SQL，两处不会对同一个码给出不同说法。
- **列显隐只影响可选列**。身份列与操作列不可隐藏——把它们藏掉会留下一张没人能据此操作的表格。隐藏列表存在 `localStorage`，按表格区分，并在读取时丢弃该表已不存在的列名（列改名不会留下幽灵）；分享出去的链接展示的是数据，不是发送者的列布局。

角色的显示名只有一处映射（`ui.tsx` 的 `roleLabel`），用户列表、用户详情、设备与会话和概览共用它：此前各页各写一份，只读运维在概览显示为“只读运维”、在用户详情与会话列表却显示成“普通用户”，同一个账号在不同页面角色不同。新增角色不会再半途落地。同理，「能否管理这个账号」也只有一处定义（`ui.tsx` 的 `canManageAccount` / `canEditAccountQuota`），与 `store.mutateAdmin` 的服务端规则对齐；此前用户列表与用户详情各写一份，批量操作本会是第三份。

### 用户批量操作

用户列表可以勾选账号并批量执行**禁用账号 / 启用账号 / 结束全部会话**。三条规则决定了它长这样：

- **范围在写入之前说明，而不是之后**。「已禁用 12 个账号」不是「哪 12 个」的答案：选错页的操作者必须能在写之前看出这一点，而不是事后从审计里还原。确认区列出将处理的账号与将跳过的账号及原因。
- **每个账号单独执行、单独报告**。有些账号是服务端**按设计**拒绝的（所有者受保护、管理员不能动同级的另一个管理员）。在第一个拒绝处停下会让其余账号静默地没做；静默跳过则会把没做的事报成成功。所以继续执行，结果按「成功 / 失败 / 跳过」分组逐个点名。
- **每账号的幂等键带上目标状态**。超时重试会重放第一次的结果，而**相反的意图**（第一次禁用、这次启用）不能被当成旧请求重放。

选择范围只限**当前页已加载的行**，界面上写明这一点：游标分页无法「选中所有符合筛选的账号」，一个暗示可以这样做的控件是最危险的一类错误——操作者会以为整个筛选范围都处理了。翻页会清空选择，避免一个看不见的选中项被作用到。

每个后台页面都会设置 `document.title`（用户详情额外带上 accountId），因为排查时通常同时开着几个后台标签，标题相同就分不清哪个是概览、哪个是日志。写操作失败在**页内**用 `Notice` 报告（`useActionError`），不再用 `window.alert`：阻塞对话框无法显示 requestId、无法被样式化，也不能让用户点进日志。

读取失败时不显示可编辑的空表单：用户详情读取失败会显示错误并提供“返回用户列表”，配额与状态保存按钮在读取成功前不可用；连接检查失败时登录页提供“重新连接服务器”，不需要刷新整页。健康检查、管理数据请求和退出请求有 30 秒超时，后台不会自动重复写操作；写请求超时不等于失败，须先刷新核实服务器结果。这些超时不改变现有账号认证库的登录/刷新协议。

配额操作与禁用/降权保护分开校验；所有者可以调整自身提交、附件配额并恢复服务器默认值。降低上限不删除已有内容，但可能限制新上传。用户名叫 `admin` 不等于角色为 Admin，请以后台显示的角色为准。并发修改通过数据版本检测：提交携带 `expectedVersion`，其他管理员已修改时返回 `STALE_WRITE` 并提示刷新，不静默覆盖。

`GET /api/admin/invites` 默认返回 25 条，支持 `limit`（1–100）、`cursor`（来自上一页 `nextCursor`）、`state`（available/used/revoked/expired）、`sort`（created/expires/state）与 `dir`（asc/desc）。筛选在分页前执行，默认按创建时间倒序，继续读取须跟随 `nextCursor`，不能再假设一次返回全部邀请码。已使用优先于撤销，撤销优先于过期，与页面状态一致；`sort=state` 复用同一段状态判定，排序与筛选不会各说一套。

**游标不包含邀请码秘密。** 游标形如 `sort~dir~值|rowid`：值是日期或状态，唯一键是 `rowid`，邀请码本身既不参与排序也不进入游标——分页 URL 会进浏览器历史、Referer 和聊天记录，把一次性凭据放进去等于把它公开。无法解析的游标返回 `INVALID_CURSOR`，与当前排序不符的游标返回 `CURSOR_SORT_MISMATCH`，两者都要求从第一页重新开始，而不是静默返回第一页或重新解释。

所有可排序的列表端点共用同一套参数：`sort`（该列表白名单内的列名）、`dir`（asc/desc，其他值 400）、`limit` 与 `cursor`。响应回显服务端实际采用的 `sort: { key, direction }`——页面与服务器各自部署，页面显示的是服务端真正做了什么，而不是它请求了什么。未知的 `sort` 名回落到该列表的默认排序（较新的页面不会因为服务端还没有这一列就整列表失败），但 `dir` 是二选一的闭集，第三个值按拼写错误报 400。

网页版每次打开记账入口先验证本站账号会话；失效时显示账号密码登录，不选择本地模式或填写服务器地址。登录与注册分开，注册需确认密码，邀请模式注册需邀请码。未初始化服务器提示联系部署者。桌面版继续保留本地/服务器选择；旧浏览器账本不读取或迁移。账本加密解锁仍独立于账号认证。

## 从异常追到账号

概览、同步诊断、运行日志、会话、审计与任务中心都以账号为可筛选维度，用户详情页另有「关联排障」入口，把同一账号的六个视图一次串起来；筛选条件进入 URL，可以直接分享或放进工单。

- 账号筛选按 `accountId` 过滤，用户名只作为显示标签：用户名改了链接依然有效。输入框同时支持按用户名或完整 `accountId` 搜索，不需要先到用户列表里查 ID。
- 时间范围用本地时间控件加「近 1 小时 / 24 小时 / 7 天 / 30 天」快捷区间；发给服务端的仍是 UTC ISO，快捷区间是「从某时刻起」的左开区间，之后的新记录会继续出现。起始时间晚于结束时间会直接提示，而不是返回空表。
- 运行日志可按账号与动作筛选（动作下拉从日志表中读取，不写死在页面里）；请求 ID 从同步诊断、日志或用户详情任一处点进去都会带着筛选打开。
- 任务中心支持 `accountId` 筛选，并把它预填进创建表单，「为这个账号跑一次校验」不需要重新输入。
- 容量告警的下一步直接进入该账号详情，而不是让管理员再到超配额列表里找人。

## 任务中心与维护

附件校验、数据库完整性校验、清理与日志裁剪都可能耗时，因此不再在 HTTP 请求内完成：接口创建任务并返回 `202`，由单执行器分批执行，执行期间登录与同步保持可用。

- 状态统一为“排队中 → 执行中 → 成功 / 失败 / 已取消 / 执行中断”，任务记录类型、发起人、目标范围、参数、开始/结束时间、阶段、已处理数量与结果摘要，另有执行记录条目。
- 取消只在批次边界生效；重新执行会创建一个新任务并记录 `retryOf`。创建、重新执行与取消共用同一套权限判断，且按**当前**操作者重新校验任务类型与目标账号，所以重试或取消一条旧任务不能绕过“备份校验/恢复演练仅所有者”与“受保护账号”的限制。
- 服务在任务执行期间退出时，重启后把失去执行者的任务标记为“执行中断”，只有带检查点的扫描（附件校验）从中断点续跑，其余保持中断状态等待人工决定。附件校验在扫描过程中按批次把检查点（最后校验对象、已处理数量、写入时间）真正写入任务记录，重启后能从该点继续；启动时还会自动调度恢复出来的任务与仍排队的任务，不需要有人打开后台才能开始执行。
- 任务只接受预定义类型与参数（例如限定 `accountId` 或已登记的备份记录 ID），不接受命令或任意文件路径。
- 任务结果区分“执行完成”与“数据健康”：接口在任务上返回 `outcome`（`clean` / `issues-found` / `failed` / `cancelled` / `interrupted` / `pending`），校验发现问题时任务状态仍为“成功”，但结果与执行记录会标注“任务执行完成，但校验发现问题”，页面用黄色标注而不是绿色“成功”，避免把执行结束理解为数据健康。
- 写接口支持幂等键，且幂等键在**执行前**就被占用并绑定发起账号：同一键会被记录一次，同一键的并发请求只执行一次；同一键换参数返回 `IDEMPOTENCY_KEY_REUSED`；同一键的请求仍在处理中返回 409 `IDEMPOTENCY_IN_PROGRESS`（提示刷新核实结果，而不是重复执行）；其他管理账号复用同一键返回 409 `IDEMPOTENCY_ACTOR_MISMATCH`（不会拿到别人记录的结果）。执行尚未产生结果就失败时会释放占用，键格式不属于 `[A-Za-z0-9._:-]{8,128}` 时返回 400。幂等记录有保留窗口。
- 健康检查 `/api/ready` 只做轻量探测（`SELECT 1` 与迁移行数），不再每次执行全库检查；`quick_check` 与深度 `integrity_check` 都由任务执行。

## 维护计划与备份保留

备份与恢复必须在服务停止时执行，所以后台**只声明计划、不调用流程**：自动备份默认关闭，且必须同时配置备份位置与维护窗口才能启用——跨字段规则在保存时和每次加载时都会检查（环境变量同样受检），一个跑不起来的计划不会显示成"已配置"。

- 计划字段：自动备份（`off`/`on`）、备份位置、维护窗口、保留的成功备份份数（默认 3）、逾期告警间隔。文本字段有自己的格式：Webhook 仍必须是 http(s) 地址，备份位置与维护窗口则是自由文本（路径不是 URL）。
- 存储页的「维护计划」区同时显示计划是否完整、最近一次校验通过的备份，以及最近一次保留清理的结果（连它自己的说明与清理份数）；如果启用了自动备份却还没有任何校验通过的备份，会明确提示去确认部署侧程序是否真的在运行。
- 备份记录列表按 25 条游标分页（`GET /api/admin/backups`，`limit` 1–200 + `cursor` + `status` + `kind`，非法值 400），返回的 `total` 是**筛选后整个集合**的条数。游标是 `created_at|record_id`，与排序键一致，同一时间戳也不会漏行或重复。
- **「最近成功备份」与「最近校验通过的备份」是整表查询，不是从当前页里挑出来的**：一页记录全是失败时，从页里 `find` 会让页面显示「暂无数据」、并让逾期告警在其实有成功备份的服务器上响起。这两个事实由 `latestBackupSummary()` 直接问数据库；列表只用来回答「最近一次**尝试**」与展示历史。
- 保留策略由部署侧执行：`npm run server:prune-backups -- --backup-dir <目录> --keep <份数> [--dry-run]`。规则是**只清理校验成功的备份**，未通过校验的一律保留并逐项列出原因，并且始终至少保留最近一个有效备份（即使份数配得比实际数量还小）。预演模式不删除任何文件。
- 每次清理都会写一条维护记录（保留份数、已清理项与大小、保留项、未通过校验项），后台读该记录来展示；`--dry-run` 也会记录，便于留下"确实预演过"的证据。
- 备份目录不在 Web 静态服务范围内；后台不读写该目录，也不提供在浏览器里下载整套服务器备份。

## 指标、诊断与告警

- 请求指标按分钟与小时分桶，内存累加、每 30 秒落库一次，避免每条请求都写库；指标与诊断事件各有独立保留策略，不受运行日志裁剪影响。资源读数（常驻内存、V8 堆、堆外内存、CPU、事件循环最大延迟）跟随同一个采样节拍写入分桶，但**保存的是分桶内的峰值而不是累加值**：这些是时点量，相加没有意义。旧分桶没有这些列时读作 0，不会被当成“当时占用为零”。
- 同步诊断只记录服务端实际接收到的同步请求及其结果代码，按错误分类给出下一步建议。
- **暴力尝试是可聚合的形状，不是日志行**：一个地址对多个账号连续失败才是攻击，而运行日志被保留策略裁剪、且每次尝试一行，「这是一个攻击者还是一个手滑的用户」在日志里要人工数。因此登录失败按来源地址聚合，账号名作为证据保留（最多列 10 个并给出总数），并单独读限流器自身的状态来回答「这个地址现在被限流吗」——**不从失败次数反推限流**，那会在服务器其实没在拦截时声称它在拦截。
- **这张视图的边界必须写在页面上**：只统计服务端记录到的失败。客户端在本地就能判定密码错误（OPAQUE 的客户端在 `finishLogin` 返回 `null` 时直接报错、根本不发请求），所以「这里没有记录」不等于「没人尝试过」。把这一点留白会让运维把一个空表读成安全。
- **限流桶的来源与用途是独立列**，不是从 `bucket_key` 里拆出来的：IPv6 地址本身含冒号，按冒号拆会把桶归到错误的地址上。旧库的桶没有这两列，显示为「未知」而不是猜一个。限流**不提供手动解封**：解封会让正在进行的尝试重新获得配额，属于应当由时间解决的窗口。
- **客户端信息**（`client_kind` / `client_version` / `protocol_version`）由客户端在 `X-Zichan-Client` 头里自报，格式为 `zichan-client/1 kind=… version=… protocol=…`。它回答的是 `deviceName` 回答不了的问题：设备名是客户端自己起的标签（常常就是「Zichan · 当前设备」），说不出构建版本。三点必须同时成立：**服务端不据此改变任何行为**（没有任何分支读它，旧客户端不发也照常同步）；**没上报就读作「未知」，不等于「旧版本」**（早于该字段的历史记录都属于这一类，把它读成旧客户端是错的）；**值解析不了就整条丢弃**，绝不返回半份信息（半份会把版本安到错误的客户端类型上）。跨域客户端的预检响应按名放行该头，否则浏览器会静默剥掉它——同步照常，只有诊断变空。
- 告警规则覆盖容量、备份失败与逾期、校验问题、清理连续失败、持续同步错误、磁盘空间，以及进程与数据库（内存接近容器上限或超过配置阈值、常驻内存持续上升、事件循环延迟、CPU 持续占用、WAL 超过配置上限、数据库空闲页可回收）：只有**连续**两个采样周期异常才生效、连续两次恢复才解除（“异常 → 正常 → 异常”不算连续），同类合并并记录首次/最后发生时间、累计次数、连续异常次数与确认人。
- 资源告警的阈值刻意取得保守，因为它们要能在真实服务器上长期安静：内存只有在**存在可比上限**时才判断（容器内存上限达到 85% 告警、95% 记为严重；没有上限则用设置项 `memoryWarnBytes` 的绝对阈值，两者都没有时不产生记录，也不留下“待确认”的空告警）；事件循环延迟默认 50 毫秒，高于 Windows 约 16 毫秒的定时器粒度，否则空闲也会持续告警；“内存持续上升”需要整个窗口（默认 12 个采样，即约 6 分钟）都在上升，且增长同时满足比例与绝对量（超过 64 MiB 且超过起点的一半），否则一个忙碌的下午看起来就像泄漏。
- 这些读数的范围只限同步服务器进程本身：桌面外壳与浏览器渲染进程不在其中，SQLite 默认未启用 mmap，所以数据库页不会计入常驻内存——页面把这个边界写在了界面上，而不是让读者自己猜。
- 告警处理闭环：确认、静默与撤销静默都走与管理写操作相同的审计事务，静默还必须带原因与 1–720 小时的到期时间。静默**不是删除**：规则照常评估、记录照常保留、恢复判断照常，只是不再发外部通知，也不再把服务状态标成“降级”（快照把这类告警单独计为 `silenced`）。
- 外部通知可选：设置项 `alertWebhookUrl`（环境变量 `ADMIN_ALERT_WEBHOOK_URL`）配置后，告警**转为活动**与**恢复**时各 POST 一条 JSON，首次观测到的历史状态不算新事件；静默期内投递记为 `skipped`。投递结果（`sent`/`failed`/`skipped` 与错误原因）写回告警并在概览页显示，同时留一条运行日志；投递失败只记录、不打断采样。留空表示只在本页展示。
- **多渠道通知**：设置项 `alertChannels`（`ADMIN_ALERT_CHANNELS`）是一段 JSON 数组，可同时配置多个渠道，
  每项为 `webhook`（`url` + `format`）或 `email`（SMTP）。`format` 决定请求体形状，因为每家服务要的信封不同：
  `generic` 发结构化 JSON，`slack`/`discord`/`feishu`/`dingtalk`/`wecom` 各发对方要求的字段，`text` 只发一行摘要。
  把通用 JSON 发给聊天服务会得到一个看起来像网络故障的 400，所以格式是显式选择而不是从 URL 猜出来的。
- **每个渠道单独投递、单独报告**：一个渠道失败不影响其它渠道，投递结果按渠道记录（`sent`/`failed`/`skipped`）。
  部分成功仍是成功，但失败渠道会写进 `notify_error`，因为“告警送到了”与“某个目的地坏了”是两件事。
- **配置了渠道列表就以列表为准**：`alertWebhookUrl` 仍被当作一个渠道继续工作，这样已有部署不需要迁移；
  但一旦配置了 `alertChannels`，就只按列表投递，不会让旧地址重复触发。
- **渠道列表解析失败是错误，不是“没配渠道”**：无法解析时投递状态记为 `failed` 并写明原因，
  否则一个写坏的 JSON 会静默变成“不需要通知”。
- **邮箱密码从不回显**：读取设置时 `password` 只返回占位符，保存时把占位符解释为“保持原值”。
  把占位符当字面密码存回去会锁死操作员自己的中继。
- **SMTP 不做静默降级**：服务器不提供 STARTTLS 而渠道要求加密时，投递失败而不是明文发送中继密码；
  地址里带换行直接拒绝（SMTP 是行协议，换行会变成新的邮件头）。邮件客户端自己实现，因为本服务只保留一个运行时依赖且被打成单文件。
- 概览页的“核心指标”支持 1 小时 / 24 小时 / 7 天区间，并可切换四条趋势序列（请求量、错误数、平均耗时、失败同步）。趋势图由纯函数几何（`trend.ts`）驱动，**没有采集到的分桶不画柱**——零流量与“还没采样”不是一回事。进程与数据库页复用同一套几何，另可切换五条资源序列（常驻内存、V8 堆、堆外内存、CPU、事件循环最大延迟），单位随序列切换（字节 / 百分比 / 毫秒）。
- 备份健康区分三件事：最近一次尝试（不论成败）、最近一次**成功**备份（校验未通过的不算成功）、最近一次校验通过。备份逾期按最近成功备份计算，失败的尝试不会推迟告警；备份存在但校验未通过会同时产生失败告警。概览页同时展示“最近成功备份”与最近一次尝试及其状态。
- 概览与告警使用轻量缓存快照（由采样任务刷新），`/api/health` 只返回身份、协议、能力与注册策略等常量，不再做账号/会话/提交的聚合。概览页的“核心指标”与服务状态用同一个 30 秒轮询一起刷新，不会出现一边新、一边旧。
- **恢复后的告警不会消失**：概览的待处理事项只列未恢复的告警（快照即如此），已恢复的记录在 `/admin/alerts` 回看。`GET /api/admin/alerts?state=resolved` 一直是支持的，缺的只是页面；告警的说明文字、下一步入口与状态标签由 `alerts.tsx` 一处提供，概览与历史页不会各说一套。

## 重型任务隔离（哈希放到工作线程）

校验任务原本在主线程上哈希：备份校验整文件读取、附件校验逐个分片哈希（单片上限 4 MiB，单对象最多 512 片）且分片之间不让出。本机实测哈希 128 MiB 需要约 89 毫秒——接近事件循环 50 毫秒告警阈值的两个周期，也就是一段登录与同步都得不到响应的窗口。

**工作线程不比主线程快，也不该更快**：同样的字节、同样的算法。本机 4 MiB 实测主线程约 2.6 毫秒、工作线程约 2.7 毫秒。变的只是**位置**：主线程在工作线程哈希期间仍能应答请求。所以阈值（2 MiB）存在的意义是**不为太小的输入付一次往返**，不是追求吞吐。

三个实现选择：

- **工作线程源码用 `eval` 传入，不额外产出文件**。构建把 `src/main.ts` 打成单个 `dist/server.mjs`；独立的工作线程文件需要单独产出并在运行时定位，内联源码则跟着打包产物走，复制到哪里都能用。
- **工作线程 `unref`，并在关闭时 terminate**。否则进程会在服务器关闭后仍不退出——这是引入线程后最实际的风险，已用「不调用 `process.exit`、观察进程自行结束」的方式验证。
- **死掉的工作线程必须让任务失败，而不是让调用方永远等待**。校验卡住不返回比明确报错更糟；同时补一个新工作线程，避免一次崩溃把所有后续哈希静默降级回主线程。

注入点刻意做成可选（`VerifyOptions.hashChunk`、`verifyServerBackup` 的 `hashFile`）：CLI 与恢复路径没有线程池，正确性不能依赖它存在。

**测量方法本身踩过一次坑**：`monitorEventLoopDelay` 在 `reset()` 之后立刻阻塞，读数会回到定时器粒度（本机约 16 毫秒），无论循环被阻塞多久——一个阻塞实现看起来完全正常。所以测试里每次测量都用**新建的直方图**而不是 `reset()`，并单独保留一条「这个仪器确实看得见阻塞」的用例守住这个陷阱。

## 进程与数据库资源

公网部署下有两类问题在别处看不出来：进程是否正在耗尽内存或被同步任务拖到不响应，以及数据库是否在按某个可解释的方式增长。这一页专门回答这两个问题，并**把“随轮询采集”和“按需扫描”分开**——这正是它的核心设计。

- **每 30 秒轮询的部分**全部是常量时间读数：进程内存（RSS / 堆 / 堆外 / ArrayBuffer）、CPU 窗口平均、事件循环延迟直方图、以及数据库的结构 PRAGMA（页数、页大小、空闲页、日志模式、同步级别、缓存、mmap、WAL 自动检查点与 `journal_size_limit`、写入等待上限）。数据库的结构读数走 `dbstat` 之外的路径，与就绪探测同级。
- **按需扫描的部分**只有一项：表与索引占用。它必须遍历整个文件的每一页（SQLite 的 `dbstat` 虚拟表），因此**不能进轮询**。本机实测：125 MiB 的库耗时约 256 毫秒，而 `integrity_check` 在同一库上约 333 毫秒——两者是同一量级，所以 `dbstat` 与深度校验一样只由按钮或任务触发，页面同时显示扫描时间与耗时，让读者知道这个数字有多新。
- 表级占用把索引单独列出（索引常常比表本身更占空间），并且**只对表统计行数**：对索引统计行数会把同一份数据算两遍。分组排序带名称次序作次要键，否则页数相同的表顺序不定，一个较小的上限可能把某张表藏起来。
- 数据库状态刻意**不提供 VACUUM 按钮**：“可回收空间”只是磁盘占用偏高的解释，真正回收需要停服执行，属于部署侧受控流程；页面给出数字与原因，不给出会破坏停服约束的操作。查询计划统计（`ANALYZE`）则可以在线执行，因此做成任务中心的 `database.analyze`，并把最近一次时间写进维护状态供页面显示。
- 接口：`GET /api/admin/resources`（`?tables=1` 才做整库扫描）、`GET /api/admin/database/stats`、`POST /api/admin/database/analyze`（创建任务，只读运维被拒）。`/api/admin/overview` 也带上进程与数据库读数，避免为了一个摘要再发一次请求。（原先并列的 `GET /api/admin/status` 已删除：它与 `/overview`、`/api/ready`、`/api/admin/settings` 完全重叠，且前端一次都不调用。）

## 会话与审计

- 管理 Cookie 为 `zichan_admin_session`，记账 Cookie 为 `zichan_session`，互不覆盖。独立显式请求头选择刷新与退出上下文；Origin 校验阻止跨站 Cookie 操作。
- 管理 Cookie 使用 HttpOnly、SameSite=Strict、会话 Cookie；生产 HTTPS 下为 Secure。服务端仍使用最多 7 天的会话有效期；后台不提供记住设备或离线管理。
- 访问令牌仅内存，不把账号密码、刷新令牌或管理数据写入 Web Storage/IndexedDB。浏览器自身密码管理器不属于应用存储。
- 并发请求共享刷新，多标签页序列化刷新。管理登录切换/退出通过 BroadcastChannel 通知其他管理标签页清空界面（在一个标签页退出后，其他标签页会明确提示并回到登录页）。旧管理请求取消或丢弃结果，不能重新填回旧数据。
- 离线退出先清空本页；若服务端撤销未确认，页面明确提示，不声称已撤销远端会话。
- 会话按会话本身分页并区分管理后台会话与记账会话；所有者会话与其他管理员的会话受保护，管理员不能管理它们。自己账号的会话可以由本人撤销（需要最近 5 分钟内登录），当前会话只能通过退出结束。
- 角色、账号状态、设备撤销、注册策略、邀请和两类配额，与审计在同一 SQLite 事务提交。审计失败会回滚变更；被拒绝或失败的尝试写独立表，不与已回滚的事务审计混在一起。**被拒绝的写操作会真的写进这张表**：`accounts`/`state`/`role` 等写路由抛出的 `ServerStoreError` 在重新抛出前记录动作、错误码、目标 accountId 与 requestId，所以概览页的"最近失败的管理操作"和管理审计页的失败区有内容可看；读请求不算管理变更，不记录。记录本身是尽力而为的：诊断写失败不会把已处理的拒绝变成 500。
- **审计保留策略**：`server_admin_audit` 原先无上限增长（logs、metrics、sync_events 都有裁剪任务，只有审计没有），`admin_audit_failures` 则是硬编码 2000 条。现在两者各有设置项——`auditRetention`（`ADMIN_AUDIT_RETENTION`，默认 50000）与 `auditFailureRetention`（`ADMIN_AUDIT_FAILURE_RETENTION`，默认 2000，即保持旧行为），并各自由每小时巡检与任务中心的 `audit.prune` 裁剪。**审计的默认上限刻意远高于运行日志**：裁剪审计是最后手段，不是日常保洁，所以它也没有被并进 `metrics.prune`——一次例行指标裁剪不该顺手缩短审计。按时间顺序只删最旧的记录。
- 审计记录操作者/目标 accountId、时间、动作、原因和前后值，默认渲染成可读句子（例如“管理员李四将用户张三的附件配额调整为 5 GiB。原因：容量申请。”）。审计可按动作、操作者、目标与时间范围在服务端筛选，并受控导出 JSON/CSV：不导出邀请码、重置码、令牌和密钥。
- 邀请码仅以 SHA-256 指纹关联，不写入可用秘密；运行日志遮盖邀请 URL 中的秘密。
- **运行日志可以导出**（`GET /api/admin/logs/export?format=json|csv`），与审计导出同样受控：沿用页面上的筛选条件、最多 5000 条、导出本身写一条 `logs_exported`。此前只有审计能导出，把日志交给别人只能截图——截图无法被撤回，附件也一样，所以脱敏不是可选项。只读运维也能导出：这正是它存在的场景。
- **日志导出的脱敏按两条独立规则做**：按**字段名**（`token`、`inviteCode`、`password`、`authorization` 等，任意深度）与按**取值形态**（32 位以上十六进制、43 位 base64url 重置码、64 位以上不透明串）。两条都要有：前者挡住以后新增的日志行把秘密放进不该放的字段，后者挡住秘密落进 `message` / `path` 这类自由文本。**账号 ID、任务 ID、请求 ID、设备 ID 与 ISO 时间戳刻意保留**——它们也是长串，但删掉导出就无法与后台对应，那正是导出的用途。

## 维护窗口与停机编排

停服备份与生产恢复必须先停掉服务本身，后台不可能调用一个必须先停掉自己的流程。所以后台能做的是三件事，缺一件这套东西就没有意义：

1. **声明窗口**：所有者（且需最近 5 分钟内的登录）在概览页声明进入维护，可带说明与计划结束时间。声明与结束都写管理审计（`maintenance-on` / `maintenance-off`），"谁在什么时候把同步停了"正是审计要回答的问题。
2. **暂停客户端写入**：`POST`/`PUT`/`DELETE` 打向 `/api/v3/*` 时返回 503 `MAINTENANCE`，带说明与 `Retry-After`。这样窗口期内做的快照不会与新的提交赛跑——这是"维护中"唯一有实际作用的部分。
3. **回答"现在能不能停"**：面板显示进行中的客户端写入数与执行中的任务数，并给出结论。这个数字从进程外部看不到，而它决定了停机会不会打断一次写入。

三个刻意的取舍：

- **只关写，不关读**。连拉取都不通的客户端没有任何办法知道自己为什么失败；后台自己的读也必须留着，否则维护模式永远关不掉。登录/注册/退出照常开放，它们不碰正在做快照的数据。
- **窗口可以自己过期**。设了结束时间的窗口到点自动恢复写入，不需要任何人操作——没人记得清的维护标志就是一次改了名字的故障。未设结束时间是允许的，但界面会明说**不会自动恢复**。
- **门禁与显示读同一个函数**（`resolveMaintenance`）。如果页面读存储的标志、门禁读过期判断，就会出现"页面显示维护中、实际写入正常"这种两边都对不上的状态。二者共用一处判断，不一致在结构上不可能发生。
- **排队任务不算停机风险**：它们还没开始，重启只会把它们标记为中断，不会丢失已完成的工作。面板照常显示数量，但不因此阻止停机。
- **拒绝一个"不会生效"的窗口**：结束时间无法解析、或已经过去，都会被 400 拒绝而不是存下来。这两种都会声明出一个实际不生效的窗口，看起来和正常窗口一模一样。

门禁按**排除读**而不是**枚举写**来实现：新加的写接口自动被覆盖。反过来做的话，每个未来的写路由都会在有人想起来之前静默绕过维护模式。这里漏掉的例外会失败在"拒绝一次读"，可见且无害。

## 管理员审核的密码恢复

1. 用户通过双方可信渠道联系管理员，请求恢复账号；目前不提供匿名工单或邮件服务。
2. 管理员在后台用户详情核实身份，勾选审核确认，发放一次性重置码，私下交给本人。此操作要求最近 5 分钟内登录。
3. 用户在记账或管理登录页展开“忘记账号密码”，输入用户名、重置码、新密码与确认密码。完成后使用新密码登录。

重置码有效期 15 分钟、仅可使用一次，重新发放使旧码失效。服务器只保存 SHA-256 摘要；页面只在当前详情内显示本次原码，不提供再次查询。账号禁用或角色变更也使待使用重置码失效。重置、撤销所有旧会话和写入审计在同一事务完成，并阻止重置前开始的登录再次建立会话。

原码到期自动隐藏，后台标签重新可见时再次检查有效期。手动隐藏或离开详情也不再显示；隐藏仅清除页面内容，不会提前撤销仍有效的码。

“撤销未使用的重置码”会清除当前待使用的一次性码并写入管理审计（动作 `password-reset-revoke`）；若没有待使用的码，操作返回 `revoked: false` 且不改变任何状态。撤销失败时页面明确提示，不会假装撤销成功。

Owner 可为 Admin/Member 发码，Admin 仅可为 Member 发码。网页管理员审核不支持为唯一 Owner 发码。Owner 使用部署者本机维护命令恢复，见 [账号安全与所有者恢复](account-security.md)。

重置保留 accountId、角色、配额和服务器上的加密账本数据。托管账本可在账号密码重置后自动恢复；私密账本仍须原恢复码或已有设备授权。
