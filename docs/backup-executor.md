# 自动备份执行器

标准服务器入口（`npm start`、`node apps/sync-server/dist/server.mjs` 和便携服务器）现在由一个监督进程管理 HTTP 子进程。自动备份默认关闭；监督进程保持心跳，启用计划后才执行停服备份。直接在代码中调用 `createSyncServer()` 的嵌入式部署不启动监督进程，后台会明确显示没有执行器心跳。

## 启用

在「系统设置 → 备份计划」配置：

1. **备份位置**：服务器上的绝对路径，例如 `D:/zichan-backups` 或 `/backups`。执行用户必须有写权限，目录不能与数据目录、公开网页目录互相包含；现有符号链接也参与路径检查。
2. **维护窗口**：`每天 03:00-04:00`、`周日 03:00-04:00` 或 `Sun 03:00-04:00`。采用服务器进程的本地时区，具体时区在「存储与备份」显示。`23:00-01:00` 表示跨午夜窗口。
3. **自动备份**：设为 `on` 并保存。若当前就在窗口内，执行器可能在几十秒内启动备份；期间登录、同步及管理页面暂时不可用。

对应环境变量保持兼容：`ADMIN_BACKUP_AUTO`、`ADMIN_BACKUP_DIRECTORY`、`ADMIN_BACKUP_WINDOW`。环境变量优先于数据库。容器部署需要另行挂载可写备份卷，例如 `/backups`，不能把备份目录放入公开网页卷或 `/state` 数据目录内。

`backupIntervalHours` 仍仅用于“多久没有成功备份”的告警，不控制调度频率。`backupRetentionCount` 仍属于已有的手动保留清理流程，本次执行器不自动删除历史备份。

## 执行与恢复

- 每 10 秒检查一次计划并记录心跳。每个窗口最多尝试一次；服务在窗口中启动会执行该窗口，窗口结束后不补跑错过的备份。
- 在停服前将窗口标识持久化并同步到磁盘。收到关闭指令后等待自己启动的 HTTP 子进程完全退出；45 秒未正常停止则取消该次备份，绝不绕过停服检查。
- 复用原有备份流程：SQLite 快照、认证与托管密钥、附件复制、文件校验及数据库检查；校验完成后才将暂存目录改名为正式备份目录。
- 成功或失败均写入 `maintenance/` 记录，并重新启动 HTTP 服务。页面分别展示最近执行、成功与校验证据、执行器上次结果。
- 正常重启沿用已消费的窗口，不会再次备份。崩溃后未结束的记录标记为中断/失败，不在当前窗口自动重试；已落盘的完成记录优先保留。时钟倒退也不会重放已经消费的窗口。
- 进程锁避免两个标准入口同时管理同一数据目录。发现另一个服务仍占用该目录时拒绝启动；执行器不会根据任意 PID 文件去终止外部进程。
- 备份失败仍会尝试恢复 HTTP 服务。若服务自身无法启动，监督进程以错误退出，部署侧进程管理器应报告失败；不能把“备份文件已写好”当成服务已恢复。

执行器状态文件为 `backup-executor.json`，锁文件为 `backup-executor.lock`。不要为了重试而删除执行状态；损坏状态文件会拒绝继续调度，避免同窗口重复执行。旧版本允许保存的自由文本窗口不会阻止管理页面启动，但执行器会显示配置错误并拒绝停服，所有者可在页面修正。

## 页面判断

「存储与备份」每 10 秒刷新，显示执行器身份、最近心跳、服务器时区、下次计划时间、上次结果和错误。心跳超过 45 秒显示“心跳已失联”，同时隐藏下次时间；缺失或不可读取显示“运行状态未知”。接口失败时不继续将旧的心跳当成在线。

监督进程与 HTTP 服务都停止时，页面只能显示连接失败，不能在线查询已停止的进程。恢复服务后，执行记录仍可追溯。

维护窗口约束**启动时间**；大备份可能在窗口结束后才完成。当前是停服全量备份，会中断正在执行的后台任务，重启后由现有任务恢复机制标记或恢复。生产恢复、隔离恢复演练和历史备份保留清理继续走原有流程，本次不新增自动恢复或删除。

## 验证

`backup-executor.test.ts` 覆盖窗口边界、跨午夜、时钟倒退、真实备份校验、并发调用去重、失败恢复、崩溃记录、目录限制和失联状态。`backup-supervisor.test.ts` 启动真实打包进程，验证停服备份、HTTP 恢复、执行器重启不重复，以及写入失败后恢复服务。`admin-backup-executor.spec.mjs` 覆盖桌面/手机的心跳、时区、结果、失联和错误显示。
