# 从 0.2.0 到 1.0.0 的生产部署与一键更新方案

> 本文为历史方案，不能照此实施生产更新。2026-11-03 起，后续补丁更新采用[生产签名包自更新](production-self-update.md)；下文 G2 的“主机执行器替换 Docker 镜像”已废弃。跨 schema 迁移、备份与写入后的回滚边界仍需在 1.0 前独立实现和验收。

本方案以本仓库的 `0.2.0` 本地发布包为历史演练起点。`0.3.0` 已发布，但仍未交付跨版本数据库迁移与 Web 一键更新；这些能力仍属于计划中的 `1.0.0`。方案参考了《TS_Docker_Web_一键更新技术方案》，并按本项目的 Docker 镜像、SQLite 和多节点复制结构调整。

## 版本边界与交付顺序

**先完成生产镜像交付能力，再实施和发布 `1.0.0`。** 镜像交付关口使用开发提交的候选镜像演练，不移动既有 `v0.2.0` 标签，也不把包含后续修复的镜像冒充为 `0.2.0` 发布物。候选镜像可用提交 SHA 标识；最终 `1.0.0` 从确定的源码提交构建一次，通过全部验收后按同一 digest 发布，不在验收后重新构建一个内容未知的镜像。

| 关口 | 交付内容 | 通过条件 |
| --- | --- | --- |
| G0：`1.0.0` 前 | 可信 OCI 镜像仓库、构建/签名流水线、固定 digest 的生产 Compose、旧镜像保留与回退演练 | Linux 测试机从仓库按 digest 拉取运行，不在目标机从源码构建；重建后身份与数据不变；故意提供坏镜像时可回到旧 digest |
| G1：`1.0.0` | 异机加密备份、整机恢复、明确时区的自动备份 | 从第二台机器保存的备份在空白 Linux 主机恢复，数据库、附件、密钥和节点身份校验通过；时区和维护窗口实测正确 |
| G2：`1.0.0` | 主机更新执行器、备份互斥、迁移、健康验收和受限回滚、Web 管理入口 | 用真实 `0.2.0` 数据执行跨版本更新及故障注入；各回滚边界按预期处理，升级任务可在断线或重启后查询 |

G0 只证明镜像**可交付**，不代表可以把真实账本切到生产环境。G1、G2 以及真实 HTTPS 入口、客户端兼容和多节点验收通过后，才可宣布 `1.0.0` 生产可用。私有 GitHub 仓库 `602star/zichan`、GHCR 候选流水线及测试机按 digest 拉取已建立；原始证据见[生产镜像交付验收](../acceptance/production-deployment-acceptance-2026-10-28.md)，现行操作见[生产部署与恢复](production-deployment.md)。本地 `docker save` 包可用于离线演练，但不能代替仓库发布与 digest 验收。

## 现有边界

- Docker 镜像同时提供 Web 和同步服务，数据位于 `/state/server`。开发 Compose 仍可在测试机从源码构建；生产 Compose 已改用 GHCR 固定 digest 的候选镜像。
- 真正的 `v0.2.0` 标签中的 Compose 只有 `zichan-data` 卷，使用回环端口映射和较宽的 `TRUSTED_PROXIES` 默认值；当前开发 Compose 的宿主机网络、独立备份卷和停止宽限期是标签之后的修改。跨版本演练必须从标签原样部署，记录原 Compose 项目名与卷名，再迁移部署配置并复用同一服务器数据，不能只在当前开发 Compose 上重装。
- `0.2.0` 的服务器数据库基线为 schema 27，本地账本基线为 schema 127，同步协议为 v3。现有启动检查只接受当前 schema；跨版本数据迁移必须在 `1.0.0` 实现和验证。
- 数据库、加密附件、`server.secret`、`custody.key`、`node-signing.key`、`server-id` 和 `opaque.server-setup` 必须随节点一起备份。恢复副本不得与原节点同时在线。
- Web 的 Service Worker 可能继续运行旧页面。服务器与旧 Web、桌面客户端之间需要明确的兼容窗口。

## 生产部署目标

每台 Linux 主机的 Compose 只运行一个业务容器；HTTPS 反向代理作为宿主机服务运行，只开放 443。业务服务通过宿主机网络仅监听 `127.0.0.1:8787`，反向代理转发到该地址、保留公共 Host，并覆盖 `X-Forwarded-Proto` 为单一的 `https`。`TRUSTED_PROXIES` 精确设为实际代理地址 `127.0.0.1`。每台节点使用独立的持久数据目录与节点身份。

当前开发 Compose 使用两个 Docker 命名卷 `zichan-data:/state` 与 `zichan-backups:/backups`。生产配置使用一个专用宿主机目录 `/opt/zichan/data/` 绑定到 `/state`，其中 `server/`、`backups/`、`runtime/` 分别保存业务状态、本机备份和已安装程序。从命名卷迁移到宿主机目录时必须先完整复制数据和权限，在隔离环境验证身份与恢复；直接换挂载会得到空数据目录并生成新服务器身份。生产脚本使用经验证的镜像 digest，Compose 不包含 `build:`，也不在目标机从源码构建。首次生成的 `server.secret` 固定保存；重启和重建容器必须复用数据，不临时生成另一把 `SYNC_SECRET`。

### G0：生产镜像交付

1. 为镜像单独建立发布流水线：从固定 Git 提交和锁文件构建，固定 Node 基础镜像 digest；先覆盖测试机的 `linux/amd64`，其他架构须各自构建和验收。现有 CI 的容器任务只测试 `docker build/run`，不发布镜像，也不验证生产 Compose。
2. 质量门通过后向选定的 OCI 仓库推送候选镜像，记录镜像 digest、源码提交、基础镜像 digest、平台、服务器 schema、同步协议、构建工具版本和测试结果。生成 SBOM/来源证明，并对镜像或发布清单签名；主机保存独立信任根，拉取前验证签名和 digest。标签仅供人查找，部署只引用 digest。
3. 提供独立生产 Compose：`image: <仓库>/<镜像>@sha256:<digest>`，保留单业务容器、回环监听、宿主机 HTTPS 代理、两个持久挂载和 30 分钟停止宽限期；明确项目名、挂载目录、`TZ` 和配额。部署预检拒绝空数据目录覆盖现有节点、不可写备份目录、错误架构和错误 digest。
4. 在 Linux 测试机演练 `pull → 验签/验 digest → 备份并校验 → 启动并等待 healthy → 核对版本/schema/serverId/节点公钥/Web`。保留旧 digest；在**无数据库迁移和新写入**的故障场景切回旧镜像并复验身份。记录镜像和回退耗时。

G0 的完成证据包括：仓库中的可拉取 digest、签名/清单、生产 Compose、测试机拉取和回退日志。完成 G0 后继续开发 `1.0.0` 功能；最终版本仍须用同一流水线生成和验收。

### G1：异机备份、整机恢复与时区

现有 `createServerBackup()` 生成本机目录备份和 SHA-256 清单，包含 `server.sqlite`、附件以及 `server.secret`、`custody.key`、`node-signing.key`、`server-id`、`opaque.server-setup`。这些密钥文件本身不是安全的异机传输包；备份运送程序必须先加密，解密凭据要在源主机之外独立保管。业务容器继续只负责生成和验证本机备份；宿主机独立的传输任务只挑选已经完成并通过校验的备份，送到第二台机器或具备版本保留能力的异地存储，上传完成后在异机复核完整性。异机存储使用与业务主机不同的凭据和保留策略，防止源机故障或误删同时清除所有备份。

自动备份默认保持关闭，直到异机传输和恢复演练通过。启用时在生产 Compose 显式设置 IANA 时区（本项目测试机用 `TZ=Asia/Shanghai`），维护窗口按该时区配置；管理页与执行器状态必须显示相同的时区和下一次执行时间。先在隔离实例测试一次窗口内备份、服务暂停/恢复和异机传输，再在正式节点启用。节点重启、错过窗口和跨日窗口也要验收，不能只检查环境变量是否存在。

整机恢复演练使用**空白主机和异机备份**，不是在原主机的另一个目录中复制：停止或隔离原节点，安装 Docker 与宿主机 HTTPS 代理，按 digest 拉取匹配的镜像，取得并解密备份，运行 `verify-backup`，恢复到空数据目录，核对 `serverId`、节点签名公钥、schema、账号、附件和代表性同步读取。恢复副本不得与原节点同时在线；验证通过后才把 443 流量切过来。现有恢复逻辑会撤销旧会话，用户需要重新登录。验收暂按 RPO 不超过 24 小时、RTO 不超过 4 小时设计：记录异机最后一份可用备份的时间与完成恢复的耗时；实施前可按实际数据量和业务要求调整目标。

## 1.0.0 的 Web 一键更新架构

采用参考方案中的版本检查、管理员操作、异步任务、进度和审计界面；执行层采用**镜像级更新**。不采用将新程序写入容器可写层或程序 Volume 的方案，因为它会让运行版本、镜像版本及容器重建后的行为分离。

```text
Owner 管理页面 → 更新任务 API → 持久化更新请求
                                  ↓
宿主机部署执行器 ← 只读取限定范围的任务与发布清单
      ↓
验证签名和镜像 digest → 拉取镜像 → 排空写入 → 停服务
      ↓
备份并校验 → 运行迁移 → 启动新镜像 → 版本和健康验收
      ↓
提交成功记录，或按回滚边界恢复
```

执行器是主机侧的独立服务，由 `systemd` 管理；Docker Socket 不挂进业务容器。业务 API 只能提交预定义的目标版本任务，不能传入任意 URL、镜像名、路径或 Shell 命令。执行器独立保存任务状态，所以新服务启动失败时仍能报告和恢复。更新页面只允许 Owner 在重新验证身份并满足管理员 MFA 后触发；读取状态可授予较低管理权限。所有更新、回滚及失败原因进入管理审计。

发布源适配层读取签名发布清单，并可分别接入 GitHub Releases、自建 Git 服务或自建更新站点。清单至少声明版本、通道、平台、镜像 digest、服务器 schema 的来源与目标版本、支持的最小客户端版本和下载大小。私有源凭据只留在主机执行器，不送到浏览器、业务容器日志或数据库。镜像和清单都需验证来源与完整性。

## 更新状态与顺序

状态为 `checking → available → pulling → verifying → draining → backing_up → migrating → starting → validating → succeeded`；任一步失败记录错误和可执行的恢复路径。任务具有持久 ID、幂等键和主机互斥锁。管理页面断线后通过任务 ID 重新查询，不将连接中断直接当成失败。

1. 预检：确认当前 `0.2.0` 身份、schema 27、镜像 digest、磁盘空间、备份目录写权限和目标发布签名；多节点部署还需确认副本组状态与其他节点没有更新任务。
2. 拉取并验证 `1.0.0` 镜像，不改动当前运行容器。
3. 先实现**新的共享维护互斥机制**，由宿主机更新执行器和容器内自动备份执行器共同持有；当前 `backup-executor.lock` 只用于防止重复启动监督进程，不能直接当作升级锁。升级先取得维护锁，再读取 `backup-executor.json` 的状态与心跳并再次确认；状态为 `running`、心跳失联或状态不可读时不停止容器，等待备份完成或推迟更新。自动备份在认领时间窗口前也须取得同一把锁，消除检查与停服之间的竞态。锁的持有者、任务 ID 和恢复规则要持久化，进程崩溃后不能仅因超时就让两个执行者同时操作数据。随后进入维护状态，拒绝新写入并等待在途写入完成。
4. 优雅停止服务；用**旧版本维护入口**创建独立完整备份并校验数据库、附件和密钥文件。真实 `v0.2.0` 的 `verify-backup` 缺省 `--record-id` 会报错，兼容执行器须显式传入该参数，或使用经旧备份格式验证过的独立校验器；不能拿后续开发提交中的修复代替旧版本验收。备份失败即恢复原服务，停止更新。
5. 由独立迁移器从 schema 27 逐步迁移至 `1.0.0` 目标结构。每步在事务内记录版本，拒绝未知或不完整结构；不清空原数据目录。
6. 用目标镜像启动唯一实例，在维护状态下核对版本、schema、`serverId`、节点公钥、`/api/ready`、Web 页面和代表性同步读取。通过后开放写入，记录成功 digest；开放后的写入问题按下述回滚边界处理。
7. 同步组逐台更新，上一台回到 `READY` 后才更新下一台。一次更新始终只作用于一台主机的一个节点。

## 回滚边界

如果没有数据库迁移，失败时切回旧镜像 digest 并保留数据。若已迁移但尚未开放写入，停止目标版本，恢复升级前完整备份，再运行旧镜像；恢复需重新登录的会话按现有备份规则处理。若 `1.0.0` 已接收写入，不自动用旧备份覆盖数据，也不直接运行不认识新 schema 的旧镜像；执行器停止进一步升级、告警，并等待向前修复或人工恢复决策。界面必须明确显示这一状态，不显示“回滚成功”。

## 必须完成的验收

- 用真实 `0.2.0` 包、持久卷和账号数据演练 `0.2.0 → 1.0.0`，覆盖数据库、附件、节点身份和客户端登录；禁止用空库或同版本重装代替跨版本测试。
- G0 用生产 Compose 从仓库按 digest 拉取候选镜像，核对签名、平台、源码提交和构建证明；故意提供错误 digest、错误架构和无法启动的镜像，确认旧镜像与数据仍可恢复。该演练不代替 `0.2.0 → 1.0.0` 的真实迁移测试。
- G1 在空白 Linux 主机从**异机**加密备份恢复，确认原节点已隔离、身份和附件未丢、旧会话失效、443 切换后登录和同步正常；记录实际 RPO/RTO。验证备份上传中断、异机校验失败、解密凭据丢失时不会误报备份成功。
- G1 显式设置 `TZ=Asia/Shanghai`（或实际部署时区），验证管理页、`backup-executor.json`、容器进程和备份窗口一致；覆盖容器重启、整机重启、跨日窗口及错过窗口。
- 在 Linux 容器中完成首次启动、备份、校验、隔离恢复、重建容器和整机重启。验证新版本无法启动、下载中断、磁盘不足、备份失败和迁移中断时的状态与恢复。
- 故障注入一项耗时自动备份，在 `running` 期间提交更新任务，确认更新延后且容器不被停止；备份结束后才继续更新。验证心跳失联、状态文件损坏和备份与更新同时抢锁时均安全失败。确认 Compose 的 30 分钟停止宽限期实际生效，不把 Docker 默认的 10 秒当作足够的优雅退出时间。
- 验证旧 Service Worker 页面和 `0.2.0` 桌面客户端的兼容行为；不兼容时明确提示升级并阻止有风险的写入。
- 浏览器与桌面本地 schema 127 的升级另设客户端迁移流程和备份验收；服务器镜像升级不得清理或重置客户端本地账本。
- 三台独立主机上逐节点更新，确认每次重启后副本组重新达到 `READY`、附件承诺与物理校验一致。
- 发布 `1.0.0` 前先提供可信镜像仓库、签名密钥和异机备份位置；发布流水线记录镜像 digest、源码提交、构建 Node 版本及验收结果。

## 实施批次

1. **`1.0.0` 前的 G0**：确定 Git/OCI 发布目标；完成镜像构建、签名清单、固定 digest 的生产 Compose、从仓库拉取部署和无迁移回退演练。此时不发布 `1.0.0`。
2. **`1.0.0` 的 G1**：完成异机加密传输、独立保管解密凭据、整机恢复工具与演练；配置和实测时区及自动备份维护窗口。
3. **`1.0.0` 的 G2 基础**：实现 schema 27 到目标版本的迁移器、真实旧数据夹具、共享维护互斥与持久更新任务。
4. **`1.0.0` 的 G2 执行与界面**：实现主机执行器的拉取、排空、备份、迁移、启动、验收和受限回滚；管理页显示版本、进度、历史与恢复状态。
5. **最终发布验收**：真实跨版本故障注入、异机恢复、旧客户端兼容、真实 HTTPS 入口和多主机滚动更新。全部通过后才将通过验收的最终镜像 digest 发布为 `1.0.0`。
