## 本轮：管理员能否「点预览看用户记账」

用户先问「管理员应该能查看用户的附件和账本，看看如何设计」，我出了方案；
用户一句「有密钥解密啊」推翻了初稿；追问「能不能点用户管理、点预览直接看他的记账」，
二稿又被自己的实测推翻。**三轮里我错了两次，两次都是同一个根因。**

### 判断（含两次自我纠错）

- **错 1：把「产品承诺」读成「能力事实」。** 初稿写「服务器没有能解密的密钥」，
  依据是 `docs/server-admin.md` 的「管理后台不提供直接读取用户密钥的接口」。
  实际：`server.ts` 的 `protectionResponse()` 每次用户登录都在 `openCustodySecret(...)`，
  把凭据明文回给客户端。我只看了 `key-custody.ts` 的文件名，**没查谁在调它**。
- **错 2：先下结论再找证据。** 二稿写「账本解不开，因为服务器不保存 `commitId`」——
  而 `sync_server_commits.commit_id` 就在建表语句里，**我上一轮甚至读过那段**。
  我看到 `contentHash = sha256(整条提交)` 就断定 AAD 不可复现，
  忘了**解密只需要 AAD 的值与加密时一致，不需要理解它的含义**。
- **正确结论**：`ledgerId`/`commitId`/`contentHash` 三个 AAD 字段全在服务端，
  托管账号的账本**可以解密**；私密账号不行（`sealed_secret` 为空）。

### 实测（本轮两次，都跑通了）

1. **解密链**：真实 server + 真实 HTTP，只用 `custody.key` + `sealed_secret` +
   `envelope_json` + `sync_server_commits` 行，解出了提交明文。
2. **重放链**（比 1 更进一步）：解出的提交 → `adoptLedgerId` + `storeSyncCommit` +
   `applyPendingCommits` → **内存库** → 读回实体。输出 `applied=1`、
   `replayedSecretVisible=true`。即「预览看到记账」整条路已通。

### 工具坑（本轮新踩）

- **`node:sqlite` 在 vitest 里无法静态 import**（`Failed to load url sqlite`）。
  照抄 `packages/db/src/drivers/node-sqlite.ts` 的写法：
  `process.getBuiltinModule('node:sqlite')`，问题消失。
- **`registerAccount` 只返回 `{ role }`，不返回 token**；要 token 得再调 `loginAccount`。
  我照直觉写了 `user.accessToken`，得到 401。
- **`store.setLedgerId` 不存在**，正确方法是 `adoptLedgerId`（会拒绝已有提交的账本）。
- **`openLedger()` 默认 `:memory:`** —— 这正是「重放不落明文」的现成路径。
- 测试 fixture 的 owner setup token 要用 `OWNER_SETUP_TOKEN` 常量，
  写死字符串会 403 `INVALID_OWNER_SETUP`。
- **探针跑通后要立刻删并移出仓库**：`.scratch-inspect/` 这类目录**不在 `.gitignore` 里**
  （`git check-ignore` 返回 1），差点被 `git add -A` 带进去。
