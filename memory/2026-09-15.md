## 三、停用扩展包的分类"看得见、筛不着"（提交 `d29a135`，本轮最难的一处）

- 现象（用户报的第二个问题）：停用扩展包后，那些分类下的旧流水在列表里照常显示分类名，
  但筛选和高级查询里**根本没有这一项**，只能把扩展包重新启用才查得了。实测：筛选搜「食堂」命中 **0**。
- 根因是**字段级陷阱**：`categoryOptions` **从不转发 `includeInactive`**（opts 类型里没有这个字段），
  被 `allCategories` 丢弃的停用行从未进入选项池 —— 而搜索只是在池子里过滤，
  **搜索找不到不存在的东西**。所以"输入可搜索隐藏分类"的提示帮不上忙：
  隐藏（`isHidden`）在池子里，停用（`isActive:false`）不在。
- 计划中途的拐点：原打算"只放停用**且仍有流水**"的分类。实测 `snap.transactions` 是**空的**
  （大账本按页从 SQL 取流水，快照只持主数据），渲染时拿不到"哪些停用分类真有流水"。
  改成复用「显示隐藏」同一套语义：停用分类进选项池、默认不占位置，搜索或开「显示隐藏」能找到。
  零新查询、零新 plumbing；代价是可能列出几个选了为空的项。
- 读/写路径分开：读路径（筛选行、高级查询取值与预览标签）用 `historicalCategoryValueOptions`；
  写路径（记账弹窗、批量修改）仍只给可用分类 —— 不给已停用分类造新引用。
- `CategoryPicker` 加第三枚徽标「已停用」，**优先于「隐藏」**（停用行同时是 hidden，
  否则用户会以为开个开关就能找回）。
- 验证：typecheck、lint 通过；单测 **821 通过**（108 个测试文件）；e2e **22/22 通过**。
  做了突变验证：去掉 `includeInactive` 后单测报 `expected [...] to include 'pet_medical'`、
  e2e 直接失败 —— 这是"测试真的在测东西"的证据。

## 四、管理页点开「物品分类」一级分类就打进错误边界（本轮新交）

- 现象（用户报的）：管理 →「物品分类」→ 点任意一级分类，整页变「这个页面暂时无法显示」，
  错误摘要 `TypeError: Cannot read properties of null (reading 'open')`。
- 根因：`Manage.tsx` 的 `FixedCategorySection` 把 `event.currentTarget.open` **读在
  `setExpanded` 的 updater 回调里**。React 只在事件分发期间保证 `currentTarget` 有效，
  监听器返回后由 `executeDispatch` 置为 `null`，而 updater 在**渲染阶段**才执行 —— 读 `null.open`。
- **为何不是每次都崩（很有价值的一条）**：`dispatchSetState` 会在事件里**同步预先求值**一次
  updater（此时 `currentTarget` 还在），渲染阶段大概率直接复用这个 eager 结果；只有该 hook 的
  更新队列发生重基（rebase，例如同一次渲染里并入了后台的其它 state 更新）时，渲染阶段才**重跑**
  updater。所以本仓 e2e 里**第一次展开正常、第二次（收起）才崩**，而用户那边页面一直有后台
  更新、一次就崩。
- 取证靠真堆栈（`page.on('console')` 抓 `error:` 项）：
  `TypeError ... at assets/Manage-*.js:1:35588` → `at Object.useState (react)`，直接指向我们的 updater。
- 为何一直没发现：e2e 套件（含 8 月以来所有回归）**从未点过**该一级分类标题，分支零覆盖。
- 修法：读取提回事件分发期间，并抽成与同文件 `CategorySection` 一致的纯函数
  `toggleExpanded(id, nextOpen)`；顺带收口 `QuickCategorySettings` 里同类写法
  （`event.target.checked` 留给 updater；`target` 不置空所以不崩，但同属隐患）。
- 教训（值得跨会话记住）：**任何"把 `event.*` 交给延迟执行的回调（setState updater / Promise /
  setTimeout）去读"的写法都是 bug**，即使当前看着能用 —— React 会回收事件对象的字段。

## 五、退款在轻量模式下“看不到、管不了、还会填错”（本轮新交，P0+P2）

- 用户提的四个疑问（退款后账单还在 / 看不到收入 / 没有部分退款 / 跟作废重复）都真实存在，
  同一根因：轻量模式把筛选强制为 `type:'expense'`，**退款行整段消失**，而原支出行不带任何“已退”状态。
- 三个具体缺陷（均有实测证据）：
  1. `本月支出 ¥0.00` 与 `合计支出 ¥100.00` 同屏矛盾（卡1走 report 聚合含退款，卡2走 browse 聚合被类型条件滤掉退款）；
  2. 部分退款把“金额”改成 30 而“冲减”仍停 100 时**静默接受**，账上把 100 全冲掉而实际只收回 30；
  3. 全额退款后成死胡同：退款按钮消失、退款行不可见、原支出因“请先作废关联退款”作废不了、
     操作历史模块默认未启用 —— 唯一退路是 10 秒撤销 toast。这就是“和作废重复”的真相。
- 交付：聚合按方向放宽类型范围（expense 纳入 refund，income 不纳入）；
  `TransactionBrowsePage.refundsByOriginal` 回传退款行摘要；行上角标显示已退额（全额则划线转灰），
  角标同时是退款记录弹窗入口（可编辑/作废）；表单在币种相同时不再显示“冲减”字段也不写入实体，
  不同币种才必填；数据库拒绝同币种下两个数不一致的退款。
- **一条重要坑**：phone 布局用 `.zc-transaction-row > :nth-child(N)` 定位子元素，
  所以改行内结构时**不能增删栅格子元素**，只能在现有第 3 个子元素内部重排 —— 否则手机卡片布局错位。
- 记录位置：仓库内 `docs/worklog.md`（逐条）与 `docs/web.md`、`docs/db.md`（现状）。

## 六、分类筛选控件在手机上只有 39px（内联高度压过触控地板，本轮新交）

- 现象：账号模式 `mobile-layout.spec.mjs` 七个视口都报
  `touch-target<44px: button#transaction-filter-category.zc-select "全部分类▼" is 254x39`。
  桌面看不出来，所以单测与默认 e2e 都没拦住。
- 根因：`CategoryPicker` 触发按钮内联 `minHeight: 38`，而触控地板是样式表里的
  `@media (pointer: coarse)` / `max-width: 767px` 中的 `min-height: 44px` ——
  **内联权重大于样式表**，那两个块永远赢不了。
- 修法是一行删除：`styles.css` 自己写明「One control height for every button, from CSS
  rather than from an inline style, so the coarse-pointer block can raise it to 44px」，
  `button { min-height: var(--control-h) }` 已提供桌面 38px —— 内联高度既多余又刚好堵住地板。
  另把这条不变式写进 `triggerStyle` 的文档注释。
- 教训（跨会话）：**控件上不要写内联高度**；内联会静默取消所有触控地板，
  而且只在真机/手机视口下暴露。
- 同类的潜在隐患（本轮**未动**，已告知用户）：另有 4 处内联 `minHeight` 小于 44 的按钮
  （`Manage.tsx:1167/1168` 附件区的 34、`ui/FirstServerConnectionGate.tsx:240` 的 34、
  `ui/FirstRunWizard.tsx:215` 的 40、`screens/Game.tsx:203` 的 42）。它们桌面上的紧凑尺寸
  是有意的，要修需先定“表格行内次要按钮在手机上要不要 44px”这个设计问题。
