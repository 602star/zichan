## 一、构成环下钻无法清除筛选（轻量模式）

- 用户一句话报的：「有 bug，点完环形分类后无法清除筛选？」没有说哪一页，先读代码定位再动手。
- 定位过程：环形分类图只有两处 —— 日常支出页的「本月支出构成」（`ExpenseCompositionCard`，
  两种模式都有）和报表页日常收支页签的构成图（环形/条形二选一）。报表页下钻后有一个
  「清除分类下钻」chip（`Reports.tsx` 日期行右侧），能清；**日常支出页没有**。
- 根因：`drillToCategory` 往 `filters.category` 写了一个分类并把区间收窄到本月，而轻量模式
  **不渲染筛选行**（`Filters` / `SavedViews` / `AdvancedQueryBuilder` 全是 `usesAccounts &&`），
  资产模式还有 `CategoryPicker` 能清，轻量模式一个出口都没有 → 只能刷新页面。
- 改法：下钻时把「被改写的区间」记进新 state `categoryDrill{category,before,after}`；
  日期行右侧出现「清除分类下钻：<分类> ×」；区间只在仍是环设的值时放回 `before`
  （用户自己改过就以用户为准）；环的图例行**再点一次 = 取消**（`toggleCategoryDrill`）。
- 验证方式（值得记）：先写 e2e 用例，然后 `git stash push -- <文件>` + 重新 build web，
  确认同一条用例在旧代码上**失败**（等不到那个 chip），再 `git stash pop` 跑绿 ——
  这样"这条测试真的抓的是这个 bug"有证据，而不是只看它变绿。

## 二、本机 e2e 环境坑（重要）

- `tools/e2e` 的 Playwright 自带浏览器是**半截安装**：`.playwright-browsers/chromium-1193/chrome-win`
  和 `%LOCALAPPDATA%\ms-playwright` 里都只有 `140.0.7339.186.manifest` + `chrome.dll`，
  缺 `chrome.exe` 与 `chromium_headless_shell-1193`，直接跑会报 "Executable doesn't exist"。
  **不要**因此去 `npx playwright install`（要下载），改用系统 Chrome：
  `$env:PLAYWRIGHT_EXECUTABLE_PATH='C:\Program Files\Google\Chrome\Application\chrome.exe'`
  （`playwright.config.mjs` / `account.config.mjs` 都读这个变量）。
- 跑单条 account/tools 用例：`cd tools\e2e; npx playwright test <spec> --reporter=list`。
  `tools/e2e/tests/fixtures.mjs` 会在进程内起一个真 sync-server（`apps/sync-server/dist`），
  所以**必须先 `npm run build:server`（或至少 build:web）**，否则测的是旧的 dist。
  `helpers.mjs` 的 `openTransactions(page)` = 轻量模式 + 停在日常支出页，正好是本 bug 的场景。
- 默认 ledger 分类里有「堂食餐饮」（food）和「公交地铁」（transport），做两分类的用例够用。

  改成 `focus()` + `press('Space')` 一次到位。

## 四、环改成两级（左环一级、右环二级）

- 用户先问「环形图需要显示二级吗？二级太多了环会很乱」→ 我先把“现在画的就是二级”这个事实核清
  （聚合在 `groupedExpenseCategories`，按叶子 `transaction.category` 分组，已用 `COMPOSITION_SLICES=5`
  压过段数），再指出真正的问题不是“段数多”而是三条：按二级取前 5 会让最大的**板块**被拆散而出不了环；
  「其他」不可点（没有 `onSelect`）；颜色按排名取，同一分类每月变色。
- 给三个选项（A 环改成一级 / B 报表页加一级/二级粒度切换 / C 保留二级但让「其他」可点），
  用户选了 **A + 点一级后在旁边重画二级**，并定下“**报表页一起改**”。
- 关键技术结论（下次别再踩）：**筛一级不能写进 `filters.category`**，那条路是二级精确匹配
  （`selectors/transactions.ts` 的 `matches` 与 `repository.ts` 的 `transactionValueSetSql('category')` 都只认叶子），
  写进去列表会是空的。正解是新增 `TransactionBrowseInput.parentCategory`，复用已有的父级值集。
- 顺带收敛了一个歧义：`TransactionFilters` 加 `parentCategory?`，资产模式的 `CategoryPicker` 本身没有
  一级选项（`historicalCategoryValueOptions` 是 `leafOnly`），所以那里用 **空选项文案**（`食品餐饮 · 全部`）
  表达“在筛一级”，而不是让控件写着「全部分类」、列表却少一大半。
- 视觉基线（`tools/e2e/visual-baselines/`）是 **gitignored 的本地快照**，不随提交走；本机那份当时还停在更早一版
  （环卡还是旧标题），所以第一次跑必红——改动后用 `npm run test:visual:update` 重生成了。
- 下次回答“环是否该显示二级”这类问题，先落一步：**看代码里环实际上怎么分组的**，
  再把“乱”拆成可验证的几条（取前 N 的偏差、不可点的段、颜色跟排名走），否则容易停在审美争论上。

## 五、图区改成上下两张整幅卡（构成在上、趋势在下）

- 用户一句话：「把这个环形图放在日常收支的下方，流水趋势的上方，不要并列，并列后二级分类看不全
  文字，或者你看看还有什么优化方式？」没说哪一页。
- 先定位：只有两个地方画构成环——侧边栏那项「日常收支」（`transactions` 屏；
  `navigationPreferences.ts` 的 `navigationLabel` 在轻量模式下把它显示为「日常支出」，
  所以用户说「日常收支」说明他在资产/账户模式）；「流水趋势」就是页底的「全部流水趋势」卡
  （`Transactions.tsx` 里的 `Trend`）。全页只有一个 `#transaction-charts`，装着 `Trend` +
  `ExpenseCompositionCard`。Reports 页没有“流水趋势”，可以直接排除。
- **先量再改**：1280 并排时构成卡 445px、卡内两环各 ~200px，图例分类名 `clientWidth=0`
  （整段省略号）。所以“看不全”不是“挤”，是**根本看不见**。
- 改法：`styles.css` 新增 `.zc-chart-stack`（恒定单列）；`.zc-chart-pair` 用 auto-fit
  （单环占满整行、双环够宽才并排）；`.zc-donut-legend` 加 `max-width: 560px`。
  顺手把图例标签加 `title`、锚点按钮改成「构成与趋势 ↓」。
- 报表页没动顺序（它本来就上下排，只有卡内两环并排）——用户若要一致再说。
- 工具经验：临时探针 spec 放进 `tools\e2e\tests\` 会被全套件收录，**用完立刻删**；

  `apps/web/dist`，不是源码），比“凭印象说改了”有力，也顺便证明新用例真能抓到这个问题。
- 顺手发现两个**旧账**：`ledger-filter-category.spec.mjs` 与 `ledger-disabled-pack-category.spec.mjs`
  各一条红，都是 `panel.getByRole('button', { name: '全部分类' })` 超时。上个提交（两级环）在
